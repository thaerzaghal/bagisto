# Risk Register

Severity: **Critical** (cross-tenant data exposure), **High** (correctness/availability), **Medium**, **Low**.

## Findings confirmed empirically by TASK-ARCH-001 (2026-08-13 feasibility spike)

The spike (PHP 8.3.33, Laravel 12.62.0, MySQL 8.0.32, stancl/tenancy v3.10.1, real Docker containers, real HTTP requests via Pest) proved the core architecture works: two tenants, each with a fully isolated physical database, correctly resolved by domain, with a real `Webkul\Product\Repositories\ProductRepository` returning only its own tenant's product in both directions. It also surfaced four concrete, previously-theoretical risks as confirmed, plus one new one:

## Findings confirmed empirically by TASK-ARCH-004 (2026-08-14, tenant cache isolation)

| ID | Risk | Severity | Status | Evidence | Mitigation |

| R22 | (Found during the cache audit, not previously documented) `prettus/l5-repository`'s `CacheableRepository::getCacheKey()` includes `$request->fullUrl()` in its cache key hash. For HTTP-triggered calls to a tenant subdomain this gave *accidental* protection against cross-tenant key collision (different tenant → different URL → different key) even before this task's fix - but **none at all** for CLI/console-triggered repository calls (e.g. inside `TenantProvisioner`, or any future artisan command touching `Channel`/`CoreConfig`/`Country`/`CountryState`/`Currency`/`Locale` repositories - the cache-enabled ones per `config/repository.php`), where `Request::fullUrl()` resolves to a synthetic default shared by every process, not a real per-tenant value. | **High** (was a real, if narrow, gap prior to this task's fix - console-triggered repository caching had zero real protection) | **RESOLVED as a side effect of R15's fix** — `CacheTenancyBootstrapper` tags the underlying store regardless of whether the accidental URL-based differentiation applies, closing the console/CLI gap structurally rather than relying on it. Verified live via the repository-cache isolation test (`TenantCacheIsolationTest.php`), which deliberately calls the cached method through `tenant->run()` (a non-HTTP path) precisely to exercise this previously-unprotected case. | `tests/Feature/Platform/TenantCacheIsolationTest.php` | Closed by R15's fix; documented separately because it was a distinct, previously-unnoticed gap in the *old* architecture, not merely a restatement of R15. |
| R23 | (Found while writing the R15/R21 fix verification tests) With `CACHE_STORE=array`, `CacheTenancyBootstrapper::bootstrap()` creates a **brand-new** `Stancl\Tenancy\CacheManager` instance on every tenancy-initialization cycle (confirmed via `spl_object_hash()` - a different object every separate `tenant->run()` call or HTTP request). Laravel's `array` store keeps its data in PHP process memory on the store object itself, so a value written in one bootstrap cycle does **not** survive into the next one, even for the same tenant. Not a leak (values never appear for the *wrong* tenant, confirmed) and not a bug in tenancy - a property of `array`'s in-process nature that makes it unsuitable for proving/relying on cross-request cache *persistence*, only cross-tenant *isolation*. | **Low** (test-environment/local-dev nuance, not a production risk since production uses Redis) | **DOCUMENTED, verified NOT present with Redis** — a real Redis container (`docker compose up -d redis`, `CACHE_STORE=redis`, `REDIS_CLIENT=predis`) was used to directly confirm cross-bootstrap-cycle persistence works correctly externally, with raw `Redis::connection('cache')->keys('*')` showing the expected `tag:tenant{id}:entries` + per-tenant-hashed value key structure. | Live TASK-ARCH-004 verification (tinker + `docs/architecture/caching.md`) | None needed for production (Redis unaffected). Worth knowing if `array` is ever used for local dev performance testing - it will not reduce DB load across requests the way it appears to on paper, only within a single request/closure. |
