### 7. Newly discovered risks (all now recorded in `RISK_REGISTER.md` as R14–R18, all evidence-backed by this live run)

1. **R14 (Critical, CONFIRMED):** `packages/Webkul/Installer/src/Http/Middleware/CanInstall` is registered as a *global* middleware in `bootstrap/app.php` and redirects **every** request — central or tenant — to `/install` unless a flat `storage_path('installed')` marker file exists. This isn't a provisioning-pipeline nuance, it's an active HTTP redirect that would make the entire platform unreachable until fixed. Fixed for the spike with zero code changes (pre-created the marker file); documented as a required one-time deployment step for production, since we never intend to run Bagisto's own Installer wizard per DECISION_LOG C13.
2. **R15 (Critical, CONFIRMED):** `CacheTenancyBootstrapper` **hard-crashes** (`BadMethodCallException`) against the default `file` cache store — not a silent leak as Phase 0 hypothesized, an outright exception on the first cache write inside any tenant context (triggered by `l5-repository`'s cache-clean listener regardless of whether result caching is even enabled). Confirms DECISION_LOG C14 (move to a tag-capable store) is a hard prerequisite for Phase 13, not a hardening nice-to-have.
3. **R16 (High, CONFIRMED):** `FilesystemTenancyBootstrapper` suffixes `storage_path()` per tenant but doesn't pre-create the standard Laravel storage subdirectory skeleton underneath, causing warnings from `l5-repository`. Separately (and independently of that bootstrapper), Bagisto's own seeders write theme/locale asset files to a shared, non-tenant-scoped path even with the bootstrapper off — direct empirical confirmation of the storage-isolation risk already flagged as R5 in Phase 0.
4. **R17 (Critical, CONFIRMED):** `stancl/tenancy`'s default `tenants:migrate` configuration only targets `database/migrations/tenant`, silently excluding all of Bagisto's package migrations. The *naive* fix (removing the `--path` restriction entirely) would have been actively dangerous — it would have also matched `database/migrations` (where the central-only `tenants`/`domains` migrations live), meaning tenant databases would receive the central tenant-registry schema too. Fixed with an explicit `--path` glob; documented as the required pattern.
5. **R18 (Medium, CONFIRMED, operational):** tenant DB provisioning requires a database user with `CREATE DATABASE`/`DROP DATABASE` privileges — a normally-scoped application DB user does not have this. The spike used MySQL root as a documented shortcut; production needs a purpose-scoped provisioning user.
6. **Test-infrastructure finding (not tenancy-specific):** this repo's `tests/TestCase.php` uses the `DatabaseTransactions` trait, but in this Laravel version that trait's rollback hook is only ever invoked internally by `RefreshDatabase` — a bare `DatabaseTransactions`-only `TestCase` does not actually roll back test writes. Worth flagging to the team independent of this task; our test works around it with explicit `afterEach` cleanup.

None of these were fabricated or extrapolated — each was hit as a real error message during this session and resolved (or, for R18, deliberately worked around with a documented shortcut) before the tests could pass.

## TASK-ARCH-004 — COMPLETE (2026-08-14). "Tenant Cache Isolation."

## TASK-ARCH-012A — COMPLETE (2026-08-14). "Close Product Import Enforcement Bypass."

Closes RISK_REGISTER.md R39, the one real product-creation path TASK-ARCH-012 left unenforced. See [docs/architecture/feature-limits.md](docs/architecture/feature-limits.md)'s "`Webkul\DataTransfer` bulk product import - RESOLVED" section for the complete design.

**The real import flow, traced end-to-end**: a product import is created via the Admin UI (`admin.settings.data_transfer.imports.store`), validated (`Webkul\DataTransfer\Helpers\Import::validate()` → `Importer::validateData()`, which always runs synchronously — Bagisto's product importer never opts into chunked/queued validation), then, once `Import::isValid()` passes, processed as multiple independent QUEUED JOBS — one `Webkul\DataTransfer\Jobs\Import\ImportBatch` per `import_batches` row, dispatched via `Bus::batch()`, which run genuinely concurrently across the queue worker fleet. Each batch job's actual persistence (`Importer::saveProducts()`) uses a raw, multi-row `insert()` that bypasses Eloquent's `creating` event — the boundary TASK-ARCH-012 built — entirely.

**Extension point, and why TASK-ARCH-012's own earlier audit was wrong to rule it out as too costly**: rather than a per-batch hook (which would have reproduced R38's race N-ways across concurrently-running batches), this hooks the import's VALIDATION phase — by the time `AbstractImporter::validateData()` returns, every row of the WHOLE file that passed Bagisto's own per-row validation is already sitting in this import's `import_batches` rows, including each row's raw `configurable_variants` column. Parsing that column the same way Bagisto's own `prepareConfigurableVariants()` does turned out to be a handful of lines, not "re-implementing a meaningful part of the importer" as TASK-ARCH-012's own audit estimated.

**Mechanism**: `Platform\Enforcement\Importers\EnforcingProductImporter` — a plain subclass of Bagisto's product importer, swapped in via a targeted `config(['importers.products.importer' => ...])` override (`Platform\Enforcement\Providers\EnforcementServiceProvider::boot()`, running after `DataTransferServiceProvider`'s own config merge). Excludes variants (parsed from `configurable_variants`) and updates (`isSKUExist()`), then asks the SAME `TenantLimits::assertWithinLimit()` TASK-ARCH-012 already built — no entitlement logic duplicated — whether the resulting root-product count is allowed. On failure, marks every surviving row invalid with a clear message, forcing `Import::isValid()` false via its one validation-strategy-independent condition — so the existing, unmodified `ImportController::start()` gate never dispatches a single batch for an over-limit import. True atomic, all-or-nothing rejection, before any persistence, with zero `packages/Webkul` modification.

**Failure UX**: uses Bagisto's own validation/error-reporting model — the generated error summary/report every other validation failure uses, not a bespoke response. Confirmed live: no internal exception name ever appears; the message names the actual limit ("your current plan allows up to N products").

**Concurrency**: does not touch R38 (still OPEN, unchanged) and does not widen it — the check's window is one synchronous method call at validation time, narrower than R38's already-accepted single-creation race, not held open across the multi-batch processing phase that follows.

**Lane B fix**: `tests/Feature/Platform/CentralDatabaseWipeGuardTest.php`'s destructive-rejection tests (4-6) assumed the active process database is always literally `bagisto_central` - true locally, false in CI (Lane B's database is correctly the disposable `bagisto_ci_platform`, which the guard correctly does not protect), so `db:wipe` genuinely executed for real against that CI job's own central tables, cascading into most of the suite. Fixed by making those tests create their own throwaway `bagisto_central`-named database and drive the guarded command via a real subprocess pointed at it - never touching the ambient default connection - with an existence-check skip guard so nothing is ever created/touched/dropped under that name if a real one already exists (i.e. local development). Every one of Lane C's 9 smoke tests failed identically on `Access denied for user ''@...` before any real assertion. Fixed by setting both to `root`, reusing each job's own already-declared, non-secret MySQL service root credentials.

**Free-tier conservation**: `platform_tests.yml` changed from `on: [push, pull_request]` to `on: workflow_dispatch` - Lanes B/C (real MySQL, Lane C also real Redis, multi-minute) no longer run automatically on ordinary pushes, only on manual trigger from the Actions tab, for deliberate milestone verification. ## TASK-ARCH-018 — Billing Domain + Provider Abstraction + Pricing (2026-08-15).

Scope-checkpoint approved as a deliberate split (task's own section 32): TASK-ARCH-018 builds the provider-agnostic billing domain and a Stripe reference adapter with **no live checkout/webhook flow** - that is TASK-ARCH-019, not started here.

**New package**: `packages/Platform/Billing`, dependency direction `Platform\Billing -> Platform\Subscriptions -> Platform\Plans -> Platform\Tenancy` (DECISION_LOG C42). `Platform\Subscriptions` remains completely unaware Billing exists; `Plan` gained no relation into Billing (a real reverse-dependency mistake caught and fixed during review - RISK_REGISTER R46).

**`PaymentProvider` contract**: two methods only (`createPayment()`, `retrievePayment()`), expressed in this platform's own terms, no Stripe-shaped naming. `PaymentResult` (a plain DTO) is the only shape any adapter may return - no provider SDK type ever crosses the boundary.

**Provider resolution**: `BILLING_PROVIDER=stripe` (`config/platform-billing.php`), resolved through `BillingProviderResolver`'s single `match` expression - an unrecognized value throws `UnknownBillingProviderException`. Credentials are read only inside `StripePaymentProvider`'s own constructor, failing clearly (`MissingProviderCredentialsException`) only when the provider is actually used, never at application boot.

**Pricing**: new central `plan_prices` table (`billing_interval`/`interval_count`/`amount_minor`/`currency`/`is_active`), a separate table from `plans` (DECISION_LOG C44) - supports monthly/yearly today, extensible without a schema change. Money is always an integer minor-units value, never a float, currency a plain normalized 3-letter code with no hardcoded USD assumption.

**Payments**: new central `payments` table - `tenant_id`/`subscription_id` (nullable)/`plan_price_id` (nullable)/`provider`/`provider_reference`/`status` (`PaymentStatus`, deliberately minimal - DECISION_LOG C46)/`amount_minor`/`currency`/failure fields/`paid_at`/`failed_at`/`refunded_at`/`provider_metadata` (raw, audit-only JSON). `amount_minor`/`currency` are a historical snapshot, copied at creation and never re-derived from `plan_price_id` afterward (DECISION_LOG C45) - proven live: changing a `PlanPrice`'s amount does not alter an already-created `Payment`'s own values.

**`BillingService::createPendingPayment()`**: the one entry point for creating a `Payment` - has no parameter through which a caller could supply its own amount/currency at all (both always copied from the given `PlanPrice`), and validates the given `Subscription` actually belongs to the given `Tenant` (`PaymentOwnershipException` otherwise).

**`PaymentLifecycle`**: mirrors `SubscriptionLifecycle`'s shape - the one entry point for every `Payment` status transition (`markRequiresAction`/`markSucceeded`/`markFailed`/`markCanceled`/`markRefunded`), with its own transition matrix (`InvalidPaymentTransitionException` for anything else). No HTTP route anywhere calls it in this task - there is no public "mark paid" endpoint. `markFailed()` changes only the `Payment` itself - proven not to touch `TenantStatus` or `Subscription` status/plan (failed-payment policy remains an explicit, deferred decision). `markRefunded()` is a local status/`refunded_at` write only, with zero provider interaction and no caller anywhere - refunds are NOT an implemented capability in this task (see `docs/architecture/billing.md`), only a representable `PaymentStatus` state.

**Stripe reference adapter**: `StripePaymentProvider` uses `stripe/stripe-php` (the raw SDK, already a dependency) directly - not `laravel/cashier` (DECISION_LOG C43, avoiding Cashier's own Stripe-shaped Subscription/Customer ownership conflicting with the already-built provider-neutral `Platform\Subscriptions` domain). Tested with zero network access via Stripe's own supported `\Stripe\ApiRequestor::setHttpClient()` test seam (canned JSON, real SDK deserialization) plus `\Stripe\PaymentIntent::constructFrom()` fixtures for pure mapping logic.

**Free-plan behavior**: provisioning a tenant still creates exactly one `Subscription` (TASK-ARCH-016's invariant, unchanged) and zero `Payment` rows - no `$0` transaction is ever created merely because every tenant has a subscription.

**Platform Admin**: a new "Prices" card on the existing plan detail page (`Platform\Admin\Http\Controllers\PlanPriceController` - list/create/update/activate/deactivate, server-owned money/currency validation, no payment/checkout action anywhere).

**25 new tests**, `tests/Feature/Platform/PlatformBillingManagementTest.php`: central-only schema proof, monthly/yearly pricing, integer-minor-units money, currency normalization, authoritative-pricing derivation, historical-snapshot proof, inactive-price rejection, Pending-start proof, ownership enforcement, the full `PaymentLifecycle` transition matrix (including an invalid-transition rejection), failed-payment TenantStatus/Subscription independence, free-subscription-needs-no-payment proof, provider resolution (success/unknown/missing-credentials), Stripe SDK response mapping (success and failure, zero network), Platform Admin PlanPrice CRUD via real HTTP, unauthenticated-access rejection, central-connection-only proof, and cross-tenant payment isolation. All 25 passing.

**Full Platform suite, DB migrations, and app boot verified**: no `packages/Webkul` modification; no `Platform\Subscriptions`/`Platform\Plans`/`Platform\Tenancy` runtime code touched (Billing depends on them, they remain unaware of Billing).

**Documentation**: `docs/architecture/billing.md` fully rewritten from Phase 0 speculation to the real implementation record; `docs/architecture/subscriptions.md` (Billing integration boundary note), `docs/architecture/platform-admin.md` (routes table + Pages section extended), `docs/architecture/security.md` (new "Billing security invariants" section); `DECISION_LOG.md` (C42-C46 new, HUMAN DECISION item 2 resolved for development/reference purposes only); `RISK_REGISTER.md` (R46, R47 - both closed, low severity).

## TASK-ARCH-019 — Stripe Sandbox Checkout + Webhooks (2026-08-15).

Attempted and completed as ONE coherent task (not split, per section 33's own fallback option) - checkout and webhook are two ends of the same pipe; a checkout with no way to reach Succeeded, or a webhook with nothing real to test against, would each be an incoherent stopping point on its own.

**Checkout flow**: `Platform\Billing\Services\CheckoutService::initiate()` - the one entry point, reusing `BillingService`/`PaymentProvider` from TASK-ARCH-018 rather than duplicating logic. Validates the `PlanPrice` and its parent `Plan` are both active, validates `Subscription`/`Tenant` ownership, reuses an existing Pending `Payment` for the same `(tenant, plan_price)` pair (double-click idempotency, DECISION_LOG C50) rather than creating a duplicate. `StripePaymentProvider::createCheckout()` (new contract method, `PaymentProvider::createCheckout()`) creates a real Stripe Checkout Session in `mode: 'payment'`, deliberately never `'subscription'` mode (DECISION_LOG C47 - avoids Stripe becoming a second subscription-lifecycle source of truth, extending TASK-ARCH-018's own Cashier-rejection reasoning).

**Tenant-facing entry point**: `Platform\Billing\Http\Controllers\Tenant\CheckoutController` (`admin.saas.checkout.index`/`.store`/`.success`/`.cancel`), a NEW package-owned route/controller/view set - not folded into `Platform\Plans\Http\Controllers\Admin\MyPlanController`, since that would make `Platform\Plans` depend on `Platform\Billing` (backwards). The existing "My Plan" page gained one plain `route()`-based "Upgrade Plan" link - zero PHP-level import from Plans into Billing. New ACL key `saas.checkout` (array of all four route names, one key).

**Success/cancel URL semantics**: read-only, proven live - visiting either return route after a real checkout-session creation leaves the `Payment` exactly `Pending`. No URL-embedded payment identifier exists to look up or spoof; both routes always show the CURRENT tenant's own most recent payment.

**Webhook endpoint**: `POST /billing/webhook/stripe` (`StripeWebhookController`), central-context only (`platform` middleware group), CSRF-exempted on its own dedicated path (`billing/webhook/*` - deliberately distinct from the pre-existing, unrelated `stripe/*` exemption belonging to `packages/Webkul/Stripe`'s own storefront webhook, a genuine near-collision caught during design, RISK_REGISTER R48). Signature verification via Stripe's own official `\Stripe\Webhook::constructEvent()` (`Platform\Billing\Adapters\StripeWebhookVerifier`, a NEW, deliberately separate contract - `Platform\Billing\Contracts\WebhookVerifier` - from `PaymentProvider`, DECISION_LOG C48). Only two event types are mapped to an outcome (`checkout.session.completed` -> Succeeded, `checkout.session.expired` -> Canceled) - every other event type is acknowledged but produces zero mutation, deliberately not subscribing to Stripe's full event catalog.

**Idempotency**: new central `billing_provider_events` table, `unique(provider, provider_event_id)` - the load-bearing, database-level invariant. `WebhookEventProcessor` wraps the entire event-processing sequence (event-row read/create, `Payment` resolution/validation, `PaymentLifecycle`, `SubscriptionLifecycle::changePlan()`, event-row completion) inside ONE `DB::transaction()` (DECISION_LOG C49) - a crash anywhere inside rolls back everything, so there is no durably-observable partial state a retry needs special handling for. A concurrent-delivery race on the event row's own creation is caught via `UniqueConstraintViolationException` and treated as a safe no-op.

**Payment success flow, proven live end-to-end**: a validly-signed `checkout.session.completed` webhook marks the `Payment` `Succeeded` via `PaymentLifecycle`, then calls `SubscriptionLifecycle::changePlan()` - the SAME method TASK-ARCH-016 built and TASK-ARCH-018's Platform Admin already uses, still funneling through `TenantPlanAssignment::assign()` as the sole writer of `tenants.plan_id`. Because `TenantEntitlements`/`TenantLimits` read `tenants.plan_id` fresh with no cache layer, `products.limit` enforcement reflects the new plan on the very next request - proven live in one test.

**Security audit, all proven by real (not simulated) requests**: client amount/currency tampering structurally impossible (no such parameter exists in the call chain); an invalid webhook signature rejected with zero mutation and zero audit row (a genuinely invalid signature, not merely an omitted one); duplicate/replayed webhook delivery fully idempotent (no duplicate `Payment`, no second plan change, no duplicate event row); amount/currency mismatches between a webhook event and its correlated `Payment` rejected; an event correlating to no known `Payment` rejected; cross-tenant payment access structurally impossible (no URL-embedded identifier to spoof); failed/expired payment events touch only the `Payment`, never `TenantStatus`/`Subscription`; secrets never logged.

**Platform Admin**: "Recent Payments" table on the tenant detail page (`TenantController::show()` - date/provider/amount/currency/status/provider reference, last 10, no raw payload rendered).

**19 new tests**, `tests/Feature/Platform/PlatformCheckoutWebhookTest.php`, covering all of the above via real HTTP requests and genuinely computed, valid Stripe webhook signatures (the exact HMAC-SHA256 algorithm `\Stripe\WebhookSignature::verifyHeader()` expects) - zero outbound network access, using the same `\Stripe\ApiRequestor::setHttpClient()` test seam TASK-ARCH-018 established for Checkout Session creation. All 19 passed on the first run after fixing one test-setup bug (a missing `STRIPE_SECRET` config value in `beforeEach()`).

**Full Platform suite, DB migrations verified central-only**: `billing_provider_events` confirmed present in `bagisto_central`, absent from every tenant database, alongside `plan_prices`/`payments`. No `packages/Webkul` modification; no `Platform\Subscriptions`/`Platform\Plans`/`Platform\Tenancy` runtime code touched beyond `SubscriptionLifecycle::changePlan()` being CALLED (not modified).

**Documentation**: `docs/architecture/billing.md` substantially extended (checkout flow, webhook endpoint, idempotency/transaction boundary, payment success/failure flows, fully-exercised security invariants, future-adapter webhook boundary); `docs/architecture/subscriptions.md` (Billing integration boundary updated - Billing now genuinely calls `changePlan()`); `docs/architecture/admin-integration.md` (checkout entry point documented); `docs/architecture/platform-admin.md` (Recent Payments); `docs/architecture/security.md` (billing invariants section rewritten as "now fully exercised, not just established"); `DECISION_LOG.md` (C47-C51 new); `RISK_REGISTER.md` (R48, closed, low severity).

**Not implemented, deliberately deferred**: `billing_accounts`, refund execution (status only), tenant self-service cancellation/downgrade, invoices, automatic renewal, failed-payment suspension policy, live Stripe sandbox E2E (no real credentials configured in this environment - deterministic test coverage is the required and sufficient bar per the task's own explicit instruction).
