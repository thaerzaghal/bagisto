# Merchant Store Essentials & First-Run Readiness

**Status: VERIFIED (TASK-MVP-003, 2026-08-16).** Investigates and confirms whether a merchant who has just completed self-service signup (TASK-MVP-001) can log into their tenant Admin and make their store usable, without hidden database/configuration work or Platform-operator intervention. Bagisto Admin remains the merchant's entire commerce-management UI - no custom Merchant Dashboard, no duplicate product/order/settings screens were built. See [provisioning.md](provisioning.md) for the channel-hostname provisioning fix this task also made, and [storefront-order.md](storefront-order.md) for the shopper-side flow this task's own Admin-side checks close the loop with.

## Finding: Bagisto Admin was already sufficient

The investigation's central question - "does a merchant need Platform to build anything beyond the existing Bagisto Admin?" - is answered **no**, for every capability checked: product/category/inventory/customer/order management, shipping/payment method configuration, channels/locales/currencies, store/theme/design settings, and staff/role management are all real, unmodified, fully-tenant-isolated Bagisto Admin screens, reachable the moment a merchant logs in. The seeded role (`id=1`, `permission_type='all'`) grants full access to all of it, correctly - `Admin::hasPermission()` bypasses the ACL check entirely for that permission type, matching what a store owner should have. Platform Admin itself remains completely unreachable from a tenant Admin session (separate guard, separate central-only middleware group, proven throughout this whole engagement) - no Platform-only concept is ever exposed to a merchant.

## Merchant product → storefront path (verified, not assumed)

`Webkul\Admin\Http\Controllers\Catalog\ProductController::store()`/`update()` call the identical `Webkul\Product\Repositories\ProductRepository::create()`/`update()` methods TASK-MVP-002 already proved auto-sync channel association and produce a fully purchasable product. Verified live: a product created through the real two-step Admin HTTP flow (`POST admin/catalog/products/create` then attribute completion via the same repository `update()`) is immediately visible and purchasable on that tenant's own storefront - no Platform intervention, no manual database work.

## Shopper order → merchant Admin path (verified, not assumed)

A real order placed through the storefront checkout flow (TASK-MVP-002) is visible through the real Admin Sales > Orders surface. `Webkul\Admin\Http\Controllers\Sales\OrderController::index()` branches on `request()->ajax()` (Laravel's `X-Requested-With: XMLHttpRequest` header - the real contract the Admin UI's own DataGrid JS uses, not the `Accept: application/json` header a naive test might reach for) to return the DataGrid JSON payload; verified this returns the correct order with the correct customer email, scoped to the tenant's own database.

## Real, pre-existing environment limitation found (not a Platform defect)

While building this verification, any Admin page rendering a product thumbnail for an item with no uploaded image (`Webkul\Admin\Http\Controllers\Sales\OrderController::view()`, the Orders DataGrid, and the plain, non-AJAX `admin/sales/orders`/`admin/catalog/products` listing pages) throws `Illuminate\Foundation\ViteException: Unable to locate file in Vite manifest` for `product-placeholders/front.svg` and `icon-add-product.svg`. This is a **pre-existing, environment-specific gap in this Docker image's compiled Admin-theme Vite manifest** - it would affect any Bagisto deployment (single-tenant or not) with this exact incomplete build, has nothing to do with multi-tenancy or Platform correctness, and is explicitly out of scope to fix here (would require either rebuilding Admin-theme frontend assets - an infrastructure concern - or modifying a `packages/Webkul` Blade view to avoid the affected helper call, which this project never does). Worked around in this task's own tests by giving the verification product a real uploaded image (`Webkul\Product\Repositories\ProductImageRepository::upload()`, the same real domain-path upload `TenantStorageIsolationTest.php` already uses) - real products with real images are unaffected, since Bagisto only reaches the broken placeholder-resolution code path when an item has no image at all. See RISK_REGISTER.md R51.

## First-login experience and the welcome banner

After signup, the merchant is redirected to `{slug}.{base_domain}/admin/login?welcome=1` (built in TASK-MVP-001). Previously this marker was inert. Now, immediately after a successful login that followed this exact link, the merchant's first Admin dashboard view shows a small, dismissible, Platform-owned banner: "Welcome! Your store is ready. [Add your first product] to start selling." - linking to the real `admin.catalog.products.index` route (the actual page containing Bagisto's own "Create Product" action). An ordinary login/dashboard visit (no `?welcome=1`) is completely unaffected - the banner's entire existence is driven by that one query parameter, with zero persisted onboarding state anywhere (no new table, no new tenant column, no session data written that outlives the parameter's presence in the URL).

**Why this needed more than "just render a banner"**: Bagisto's own `Webkul\Admin\Http\Controllers\User\SessionController::create()` (the real `GET /admin/login` handler) unconditionally overwrites `session('url.intended')` on every render, based on the HTTP Referer header (`url()->previous()`) - never the current request's own query string. Since the merchant arrives at the login page via a cross-domain redirect from the central `/join` signup flow, the Referer never contains `admin`, so Bagisto's own logic always falls back to a bare `route('admin.dashboard.index')` with no query string - `?welcome=1` would otherwise be silently dropped before `SessionController::store()`'s own `redirect()->intended(...)` call ever ran. `Platform\Signup\Http\Middleware\FlagFirstLoginWelcome` closes this gap: it lets the real controller run first (`$next($request)`), then - only when the current route genuinely is `admin.session.create` with `?welcome=1` present - overwrites `session('url.intended')` with the dashboard URL carrying the same marker forward, so the subsequent successful-login redirect lands there instead.

**Extension mechanism, and the one that did NOT work (RISK_REGISTER.md R50)**: the first implementation attempted the identical per-route middleware-attachment pattern `Platform\Tenancy\Providers\TenancyServiceProvider::attachTenancyToImageCacheRoute()` (TASK-ARCH-005/R25) already uses successfully for a different route (`imagecache`) - looking up `admin.session.create` by name inside an `$this->app->booted(...)` callback and calling `->middleware([...])` on the route object. Empirically verified (real debug logging, both via `artisan tinker` and an actual failing Pest run) that this specific route genuinely does not exist yet in the router's route collection at the moment ANY `booted()` callback fires in this application, even though `AdminServiceProvider::boot()` registers it via a plain, unconditional, synchronous `require` with no lazy/conditional loading found anywhere in that call chain - while the R25 mechanism, checked side-by-side in the same environment, still works correctly for `imagecache`. The exact root cause was not fully isolated within this task's scope (a real, narrow, documented gap in this project's own understanding of its bootstrap sequence - see R50) and no working fix was found using that approach. **Working solution instead**: `FlagFirstLoginWelcome` is registered as an ordinary member of the `web` middleware group itself (`bootstrap/app.php`'s `appendToGroup('web', [...])` - the same, already-established extension point TASK-ARCH-003 used for `InitializeTenancyByDomain` and TASK-ARCH-014 for `TenantAccessGate`, a project file, never `packages/Webkul`), with the narrow-targeting logic moved inside the middleware itself via `Request::routeIs('admin.session.create')` (safe to call from `web`-group middleware, since Laravel has already matched the route by the time group middleware runs). Zero `packages/Webkul` modification either way.

The dashboard banner itself uses Bagisto's own officially-supported `view_render_event()` extension point (`bagisto.admin.dashboard.overall_details.before`, the first hook in `packages/Webkul/Admin/src/Resources/views/dashboard/index.blade.php` - the same mechanism `Webkul\Core\Providers\CoreServiceProvider` itself already uses for its own small template injections), not a Bagisto core view edit.

## Store configuration / branding readiness

Confirmed sufficient via existing Admin Settings (locale/currency/theme/design) - normal, expected merchant setup work in every Bagisto deployment, not a SaaS-specific gap. No change made.

## Per-tenant timezone - final status: deferred, not fixable without Bagisto core work

`config('app.timezone')` (default `Asia/Kolkata`, Bagisto's own upstream default) is a single, process-wide `.env` value with no per-tenant or per-channel override anywhere in Bagisto's own config surface - every tenant on this platform shares one timezone regardless of actual location. Investigated and confirmed a genuine Bagisto architectural characteristic, not a Platform provisioning gap - closing it would require adding tenant-aware timezone resolution to Bagisto's own date/time handling, a `packages/Webkul` change this project does not make. Deferred permanently, not just for this task; revisit only if a future task's brief explicitly asks for Bagisto core extension work.

## Merchant Admin isolation (verified, not assumed)

Tenant A's Admin session cannot reach Tenant B's product data - requesting Tenant B's own product id via Tenant A's domain/session either 404s (the id does not exist in Tenant A's own database) or, if it happens to collide with a different product Tenant A itself owns, never shows Tenant B's identifying SKU. Consistent with every other tenant-isolation proof in this engagement - physical database-per-tenant isolation, not an application-level filter that could be forgotten.
