# Security Threat Model

Tenant isolation is treated as a **critical security boundary**, not a data-hygiene nicety. Each row below: risk, current-codebase evidence, and the specific mitigation this architecture commits to.

| Threat | Evidence / why it's plausible here | Mitigation |
|---|---|---|
| Cross-tenant database access | Confirmed no code hardcodes a connection ([system-overview.md](system-overview.md)) — good, but means correctness depends entirely on the tenant-resolution middleware running first, every time, on every request path (web, queue, scheduled command). | Physical DB-per-tenant (strongest possible boundary — a bug can't leak data across a connection that was never opened) + `stancl/tenancy` bootstrapper ordering enforced ahead of all Bagisto middleware (R9) + automated cross-tenant test in every relevant phase (5, 6, 13, 14, 15). |
| Domain spoofing / central-domain access to tenant data | No existing domain-routing code to audit (none exists yet) — this is entirely new code we're writing, so the risk is in getting the *new* code right, not in inherited Bagisto behavior. | `stancl/tenancy`'s `PreventAccessFromCentralDomains` + explicit `central_domains` allowlist; unmatched non-central domains 404, never fall back to a default tenant (deliberately overriding Bagisto's own `Core::getCurrentChannel()` fallback-to-first-channel behavior, see [domain-routing.md](domain-routing.md)). |
| Authorization bypass between platform and tenant admins | Bagisto's `Role`/ACL system has no tenant-scoping column (`packages/Webkul/User/src/Models/Role.php`) — if platform-admin were (incorrectly) modeled as extra permissions inside the shared `admins`/`Role` tables, a compromised tenant-admin credential could theoretically be escalated. | C12: separate `platform` guard, separate central-DB model, zero shared credential surface with any tenant's `admins` table — enforced by database-per-tenant physical isolation, not application-level role checks alone. |
| Cached data leakage | R1/R2/R3 — full-page cache, catalog API cache, PhonePe token cache all currently key without tenant scoping. | [caching.md](caching.md) — `CacheTenancyBootstrapper`, response-cache disabled until verified (C15), dedicated regression tests including direct cache-store key inspection. |
| File leakage | R5 — product images / import-export files use relative, non-tenant-prefixed paths today. | [storage.md](storage.md) — `FilesystemTenancyBootstrapper`. |
| Queue/job leakage | R6 — 8 job classes resolve tenant-unaware state on the worker. | [queues.md](queues.md) — `QueueTenancyBootstrapper`, per-job dispatch tests. |
| Search leakage | R4 — Elasticsearch client singleton + non-tenant-scoped index naming (opt-in feature). | [search.md](search.md) — per-tenant index prefix + singleton reset via listener. |
| Session leakage | `SESSION_DOMAIN` is unset by default (`.env.example`), which scopes cookies to the exact host — favorable by default, but a future change to a wildcard domain (e.g. for a misguided "single sign-on across tenant subdomains" feature) would reintroduce this risk. | Explicit rule: never set `SESSION_DOMAIN` to a wildcard without a dedicated SSO design review (not in MVP scope). `sessions` table lives inside each tenant DB (session data is tenant data). |
| Logs / exports / imports crossing tenants | `DataTransfer` package writes to the `private` disk with relative paths (same mechanism as R5). | Covered by [storage.md](storage.md)'s filesystem bootstrapper — exports/imports are files, same isolation mechanism applies. |
| Admin impersonation ("login as tenant" support tooling) | Not present in Bagisto today; would be new functionality if built. | If built (not in MVP scope), must require explicit audit logging of every impersonation session, time-boxed access, and must never involve sharing/copying a tenant admin's actual password hash — implemented as a platform-admin-initiated, separately-authenticated action, not a credential bypass. |
| Tenant lifecycle access (suspension + every other non-Ready status) | No existing lifecycle-traffic concept in Bagisto (single-tenant app has no notion of "suspended"/"pending"/"failed"). A tenant whose `domains` row already exists (created at tenant-creation time, before provisioning even starts) could otherwise resolve and initialize tenancy normally regardless of its actual readiness. | **IMPLEMENTED (TASK-ARCH-013 for `Suspended`, generalized to every status by TASK-ARCH-014).** `Platform\Tenancy\Http\Middleware\TenantAccessGate`, the highest-priority entry in the `web` middleware group — resolves the tenant from a plain central `tenants`/`domains` query and rejects with `423 Locked` (`Suspended`) or `503 Service Unavailable` (`Pending`/`Provisioning`/`Failed`/`Deleting`/`Deleted`, and, by fail-closed construction, any unrecognized status) before `InitializeTenancyByDomain` (and therefore the tenant DB connection) ever runs, for Shop, Admin, and API requests alike. Proven live with a `DB::listen()` query-connection probe, not just an internal-flag inference, including against a tenant with no physical database at all — see [domain-routing.md](domain-routing.md) "TASK-ARCH-014" and `tests/Feature/Platform/TenantAccessGateTest.php` (tests 11-12). A blocked tenant's own data/database (where one exists) is completely untouched; only new requests are rejected. Platform Admin's own trusted provision/retry/remigrate/reactivate operations remain fully functional against a non-Ready tenant (`TenantAccessGateTest.php` test 16) — the gate only ever intercepts real inbound HTTP traffic, never internal `$tenant->run()` calls. |
| Central domain accidentally serving tenant data (or vice versa) | New code, no inherited risk, but easy to get wrong given `stancl/tenancy`'s central/tenant split is unfamiliar territory for a team used to single-tenant Bagisto. | `PreventAccessFromCentralDomains` + a dedicated integration test asserting platform-admin routes 404/403 when accessed via any tenant subdomain, and vice versa. |
| Billing amount/currency tampering, cross-tenant payment access, unverified "success" claims, webhook signature forgery/replay | Real checkout + webhook flow (TASK-ARCH-018/019) - every invariant below is now fully exercised by real HTTP requests and real, validly-computed webhook signatures, not just structurally established. | See "Billing security invariants" below. |

## Billing security invariants (TASK-ARCH-018, fully exercised TASK-ARCH-019)

- **The client never supplies the authoritative amount or currency.** `Platform\Billing\Services\BillingService::createPendingPayment()`/`CheckoutService::initiate()` have no parameter through which a caller could pass its own amount/currency at all - both are always copied from the given `PlanPrice` row. `CheckoutController::store()` reads only `plan_price_id` from the request.
- **Tenant/payment ownership is enforced structurally**, not by convention at each call site - `BillingService` throws `PaymentOwnershipException` if the given `Subscription` does not belong to the given `Tenant`. The checkout result page has no URL-embedded payment identifier at all to spoof - it always shows the CURRENT tenant's own most recent payment.
- **Provider selection is server-controlled** (`BILLING_PROVIDER` env var) - never a client-supplied value, and `BillingProviderResolver` fails loudly (`UnknownBillingProviderException`) for any unrecognized value rather than silently defaulting.
- **A payment cannot be marked `Succeeded` from a client request.** `Platform\Billing\Services\PaymentLifecycle`'s transition methods are called ONLY from `Platform\Billing\Services\WebhookEventProcessor`, itself called ONLY from the signature-verified `StripeWebhookController` - there is no "mark paid" endpoint anywhere, and the checkout success/cancel routes are read-only.
- **Webhook signatures are verified using Stripe's own official mechanism** (`\Stripe\Webhook::constructEvent()`) - an invalid signature returns a clean 400 with zero `Payment`/`Subscription` mutation and zero audit row created, proven by test with a genuinely invalid (not merely omitted) signature.
- **Replayed/duplicate webhook events are idempotent** - the database-level `unique(provider, provider_event_id)` constraint on `billing_provider_events`, combined with wrapping the entire event-processing sequence in one `DB::transaction()`, means a redelivered event neither creates a duplicate `Payment` nor re-runs `SubscriptionLifecycle::changePlan()` a second time - proven by test (duplicate delivery of an identical, validly-signed event).
- **Amount/currency mismatches between a webhook event's own reported values and the correlated Payment's stored snapshot are rejected**, never activating a plan on ambiguous correlation - proven by test.
- **An event whose provider reference correlates to no known Payment is rejected**, recorded for audit, never guessed at or acted on - proven by test.
- **A provider reference is never trusted as proof of payment on its own** - `PaymentProvider::retrievePayment()` exists specifically so a caller can re-verify a payment's true state directly against the provider, rather than accepting an unverified claim.
- **The browser "success" redirect never proves payment.** `CheckoutController::success()`/`cancel()` only ever READ the tenant's current `Payment` status from the database - proven by test that the Payment remains `Pending` after visiting either return route, even with a real, already-created checkout session.
- **Money never leaks through as a float.** `amount_minor` is an integer at every layer (PHP, schema, PlanPrice, Payment) - no code path in this domain represents currency as a decimal that could be rounded/truncated unpredictably.
- **Secrets are never logged.** `STRIPE_SECRET`/`STRIPE_KEY`/`STRIPE_WEBHOOK_SECRET` are read only inside `StripePaymentProvider`/`StripeWebhookVerifier`'s own constructors/methods to build SDK clients or verify signatures; no code path echoes, logs, or serializes them.
- **The webhook endpoint runs in central context only** (`platform` middleware group - no tenant DB connection is ever established for this request) and is CSRF-exempted on its own dedicated path (`billing/webhook/*`, deliberately distinct from the pre-existing, unrelated `stripe/*` exemption `packages/Webkul/Stripe` already owned).

See `tests/Feature/Platform/PlatformCheckoutWebhookTest.php` for the full, real-HTTP proof of every invariant above.

## Required automated tests proving tenant isolation (Section 21/Section 20 requirement)

At minimum, before Phase 16 sign-off:
1. Tenant A cannot read Tenant A's products via Tenant B's authenticated admin session, domain, or API — attempted from all three angles, not just "different domain returns different data" (which could pass even with a shared-connection bug if the bug happens to also break the query, masking rather than proving isolation).
2. Direct DB-connection-level test: assert the Eloquent connection resolved during a Tenant A request is literally a different database name than during a Tenant B request (inspect `DB::connection()->getDatabaseName()`), not just behaviorally different results.
3. Cache-store key inspection (see [caching.md](caching.md)) — not just behavioral testing.
4. File-path inspection for at least one upload flow — assert the stored path is tenant-prefixed, not just that download-by-tenant-A can't reach tenant-B's URL.
5. Queue payload inspection — assert a dispatched job's serialized payload actually contains tenant identity, not just that it happens to behave correctly in a single-worker test environment (a single-worker test can hide a bug that only manifests with concurrent multi-tenant job processing).
6. Suspended-tenant access attempt — direct URL access to a suspended tenant's admin/storefront/API returns the suspension page/`423`, never a 500 that might leak stack-trace details or, worse, ever falls through to serving normal content. **DONE (TASK-ARCH-013)** — `tests/Feature/Platform/TenantSuspensionTest.php`, tests 8-11 (all three surfaces, plus the direct tenant-DB-connection-never-touched proof).
7. Non-ready-tenant access attempt (`Pending`/`Provisioning`/`Failed`/`Deleting`/`Deleted`) — direct URL access to a non-Ready tenant's admin/storefront/API returns the generic unavailable page/`503`, never a 500, and never touches the tenant database connection even where none physically exists. **DONE (TASK-ARCH-014)** — `tests/Feature/Platform/TenantAccessGateTest.php`, tests 2-13 (all statuses, all three surfaces, the direct tenant-DB-connection-never-touched proof, and cross-tenant isolation). **Narrower caveat, since closed (RISK_REGISTER.md R58, TASK-MVP-003B)**: this item 7 was briefly NOT fully true for one specific route family - `/admin/dashboard`/`/admin/reporting/*`, where a Laravel routing internal (`Route::gatherMiddleware()`) eagerly instantiates the matched controller BEFORE `TenantAccessGate` (or anything else) gets a chance to run, raw-500ing a non-Ready tenant on those routes specifically even though the critical DB-isolation property (see item above) held throughout. Fixed by extending `Platform\Tenancy\Providers\TenancyServiceProvider`'s early `RouteMatched` listener (already added for R57, below) to also reject non-Ready tenants immediately, before that eager instantiation - see [domain-routing.md](domain-routing.md) "TASK-MVP-004B/TASK-MVP-003B" for the full mechanism. Two narrower, separate, still-open gaps in the SAME route family (RISK_REGISTER.md R61/R62) remain: a post-response-only internal crash-and-log event invisible to any real client, and an unknown (non-tenant) domain hitting the same route family still raw-crashing instead of a clean 404 - neither is a data-isolation or access-control defect, both deliberately left open rather than folded into R58's own fix.

8. Ready-tenant Admin dashboard first-visit (`/admin/dashboard`, `/admin/reporting/*`) — a Ready tenant's controller-eager-construction probe (the same Laravel internal referenced in item 7) must run against the CORRECT tenant database, not central. **DONE (TASK-MVP-004B, RISK_REGISTER.md R57)** — `Platform\Tenancy\Providers\TenancyServiceProvider`'s early `RouteMatched` listener pre-initializes tenancy for a Ready tenant only, before that eager probe runs; proven live via a real subprocess (`tests/Feature/Platform/AdminDashboardTenancyTimingTest.php` - Pest's in-process testing does not reproduce this bug at all).
