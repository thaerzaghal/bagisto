# Decision Log

Status legend: **STANDING** = accepted per the original brief, confirmed compatible with repo evidence. **PROPOSED** = new decision surfaced during discovery, needs approval. **HUMAN DECISION REQUIRED** = cannot proceed without explicit sign-off.

## Standing decisions (from original brief, confirmed against repo evidence)

**C1. Bagisto remains the commerce core.**
Confirmed feasible: no model/repository/DataGrid class hardcodes a DB connection, and the Concord + repository-pattern architecture is coherent enough to leave untouched.

**C2. SaaS functionality is implemented as custom modules/packages.**
Confirmed pattern exists to copy: every Webkul package is `Providers/{Name}ServiceProvider.php` + `Providers/ModuleServiceProvider.php`, registered in `bootstrap/providers.php` + `config/concord.php`. Our packages will follow the same shape but live under `packages/Platform/*` (see C11 below).

**C3. Database-per-tenant is the selected isolation strategy.**
Confirmed as viable. `stancl/tenancy` v3.10.1 supports it natively and is compatible with this repo's Laravel 12 / PHP 8.3–8.4 stack (verified against Packagist: `php: ^8.0`, `illuminate/support: ^10.0|^11.0|^12.0|^13.0`, last updated 2026-08-08).

**C4. Central database stores platform-level SaaS data.**
Confirmed. See [docs/architecture/database-per-tenant.md](docs/architecture/database-per-tenant.md) for schema.

**C5. Tenant databases contain Bagisto commerce data.**
Confirmed. Standard Bagisto schema, unmodified, migrated per-tenant using the same package migrations Bagisto already ships (`Database/Migrations` per package, Concord-registered).

**C6. Tenancy package selection is based on actual compatibility.**
Done — see ADR-003.

**C7. Payment provider is initially an architectural abstraction.**
Confirmed appropriate: `laravel/cashier ^16.0` is already a dependency but is completely unused in this codebase (no `Billable` trait, no `Laravel\Cashier` import anywhere) — a clean slate. See ADR-004.

**C8. No unnecessary Bagisto core modifications.**
Confirmed achievable for everything identified in Phase 0. The one item requiring the most care is the Elasticsearch client singleton (`packages/Webkul/Core/src/Providers/CoreServiceProvider.php:131-134`) — addressed via `app()->forgetInstance()` from our own listener, not a core edit. No other core edit has been identified as necessary. If one is discovered later, it must follow the process in the brief (identify reason → why extension can't solve it → smallest possible diff → document as ADR → assess upgrade impact) before being made.

**C9. Retail is the initial vertical.** Unchanged — no repo evidence bears on this; it's a product decision, not a technical one.

**C10. Restaurants are future scope.** Unchanged, same reasoning as C9.

## New decisions surfaced by repository evidence (PROPOSED — need approval)

**C11. Custom SaaS packages live under `packages/Platform/*`, not `packages/Webkul/*`.**
Why: `packages/Webkul/*` is upstream Bagisto's own namespace. Every future `bagisto/bagisto` release can add, rename, or restructure packages inside it. Placing our code in that namespace risks a direct collision on `git pull upstream` (e.g., if Webkul ever ships a package literally named `Tenant` or `Billing`). A sibling `packages/Platform/*` directory with its own Composer PSR-4 namespace (`Platform\`) guarantees upstream merges can never touch our code, and vice versa. This mirrors C8/C1's "don't touch core" intent one level deeper than the brief specified.

**C12. A third auth guard (`platform`) is added for platform administrators, kept in the central database, entirely separate from Bagisto's `admin` guard/model.**
Why: Bagisto's `Role`/ACL system (`packages/Webkul/User/src/Models/Role.php`) has no channel/tenant/store scoping column — it was built for one Bagisto instance's admins. Trying to overload it to also represent "platform staff who can see all tenants" would require a core schema change. Database-per-tenant naturally solves this instead: platform admins are rows in a central-DB table under their own guard, tenant admins remain ordinary Bagisto `admins` rows inside each tenant's own database, completely unmodified. See ADR-002.
**IMPLEMENTED (TASK-ARCH-011).** `config/auth.php`'s `platform` guard / `platform_admins` provider, backed by `Platform\Admin\Models\PlatformUser` (table `platform_users`, central migration). See C20-C22 below for the specific routing/UI/package-structure decisions made while building it, and [docs/architecture/platform-admin.md](docs/architecture/platform-admin.md) for the full design.

**C13. Tenant provisioning reuses Bagisto's own `BagistoDatabaseSeeder` and package migrations, not a bespoke reimplementation, but does NOT reuse the `packages/Webkul/Installer` artisan command or its `.env`-rewriting / flat-file "installed" marker.**
Why: `Installer/src/Console/Commands/Installer.php` writes DB credentials into the app's single `.env` file and marks completion with `storage_path('installed')` — both are global, single-tenant assumptions that cannot represent "N tenants, each independently provisioned." The *seeders* it calls (`Installer/src/Database/Seeders/*/DatabaseSeeder.php` via `BagistoDatabaseSeeder`) are reusable as-is against a dynamically-bound tenant connection. See ADR-001 and [docs/architecture/provisioning.md](docs/architecture/provisioning.md).

**C14. Default cache store must move from `file` to a taggable/prefixable store (Redis recommended) before multi-tenant cache isolation can be guaranteed in production.**
Why: `stancl/tenancy`'s `CacheTenancyBootstrapper` needs a store it can safely key-prefix per tenant. `file` cache store works but the FPC/response-cache full-page cache (`RESPONSE_CACHE_ENABLED=true` by default) and several `Cache::remember()` call sites (`Webkul\Shop\Helpers\CatalogApiCache`, `Webkul\PhonePe\Payment\PhonePe`) build cache keys today without any tenant component. This is not a core-modification question — it's an infrastructure/config decision. Flagged **HUMAN DECISION REQUIRED** below because it affects hosting cost and ops complexity, not just code.

**C15. Full-page response caching (`spatie/laravel-responsecache` / `Webkul\FPC`) is disabled by default for the SaaS build until tenant-scoped cache keys are verified end-to-end, and re-enabled per-tenant only after Phase 13 (cache isolation) testing passes.**
Why: `RESPONSE_CACHE_ENABLED=true` ships as the Bagisto default and the cache key hasher (`packages/Webkul/FPC/src/Hasher/DefaultHasher.php:30-38`) scopes only by channel/locale/currency **code strings** — if two tenants both use a channel coded `default` (a very likely default value), their full-page HTML could collide in a shared cache store. This is the single highest-severity cross-tenant leak risk found in Phase 0 discovery. See [RISK_REGISTER.md](RISK_REGISTER.md) R1.

**C16. A minimal slice of Phase 9 (plan/feature-definition/tenant-assignment/entitlement-resolution domain only) is pulled ahead of Phase 7, executed as TASK-ARCH-008 — phases are not renumbered.**
Why: Phase 7 (Tenant Admin Integration)'s acceptance criteria assumes real plan/usage data exists to display. Building Phase 7 first (as originally numbered) would mean either placeholder/stub UI or a rework once real data exists later — the product owner explicitly rejected building placeholder Subscription/Billing/Usage UI merely to prove the already-understood `menu.php`/`acl.php` config-merge mechanism (confirmed viable since Phase 0). Renumbering the phases themselves was rejected too, to avoid making every existing cross-reference in this document set confusing. Instead, only the narrow data/service layer of Phase 9 was pulled forward; usage tracking, enforcement, and subscription-aware overrides remain in Phase 9's later, still-unstarted completion. See IMPLEMENTATION_PLAN.md's "RESEQUENCING NOTE" on Phase 7 for the full record.

**C17. The Phase 0-sketched `subscription_plans` table is implemented and renamed to `plans`.**
Why: TASK-ARCH-008 explicitly excludes subscriptions ("This task is NOT subscriptions") — naming the table after a domain concept (subscriptions) that doesn't exist yet in this codebase read as actively confusing, especially since a future reader could reasonably (and wrongly) assume `subscription_plans` implies subscription lifecycle fields belong there now. `plans` is unambiguous (no other "plan" concept exists in this codebase) and the rename costs nothing structurally — `plan_features.plan_id` and the future `subscriptions.plan_id` both simply FK to `plans.id` either way.

**C18. `tenants.plan_id` (a direct, nullable FK column) represents "the tenant's current effective plan" — not a separate `tenant_plan_assignments` table.**
Why: Phase 0's own central-schema sketch (`database-per-tenant.md`) already proposed `plan_id` directly on `tenants`; TASK-ARCH-008 was asked to reason about this explicitly rather than assume it, and confirmed it's still the right call for now. A separate assignment table would add a join for the single most common read (`tenant → plan`) with no present benefit — there is exactly one active plan per tenant right now, no history to preserve yet.

**Phase 10 wording, revised in the TASK-ARCH-008 cleanup round**: current implementation uses `tenants.plan_id` as the pre-subscription current-plan source of truth. During Phase 10, we will explicitly decide whether it remains as a synchronized denormalized pointer or is replaced by active-subscription resolution. We are deliberately **not** committing now to "`tenants.plan_id` becomes a synced cache of the active subscription's plan" as a permanent design — that would create a future synchronization invariant (a listener that must keep two tables consistent forever) before `subscriptions` even exists to justify it. No schema change is required today either way; both directions remain fully open when Phase 10 actually starts.

**C18 FINALIZED (TASK-ARCH-016): Option C - Subscription is the lifecycle source of truth; `tenants.plan_id` remains a synchronized "current plan" pointer, written exclusively by `TenantPlanAssignment::assign()`.** Two alternatives were weighed at the start of TASK-ARCH-016 and rejected: (A) `tenants.plan_id` alone, `Subscription` as a passive side record — rejected, since it lets the two values silently drift with no single source of truth; (B) `Subscription` as the *only* source of truth, `tenants.plan_id` removed entirely — rejected, since it would force `TenantEntitlements`/`TenantLimits`/every enforcement call site (all already proven, heavily tested, zero-cache code) to change its query shape, for no benefit proportionate to the rework risk. Option C costs nothing new to implement: the synchronization mechanism (`TenantPlanAssignment`, already built in TASK-ARCH-015) already existed - `Platform\Subscriptions\Services\SubscriptionLifecycle` simply calls it internally on every plan-affecting transition (`start()`, `startTrial()`, `changePlan()`), rather than a new, separately-maintained synchronization invariant being invented. See docs/architecture/subscriptions.md "C18 finalized" for the full record and the invariant proof.

**C19. `Platform\Tenancy\Services\TenantProvisioner` depends on `Platform\Plans\Models\Plan` — the one deliberate exception to "Platform\Plans depends on Platform\Tenancy, never the reverse."**
Why: every other integration point in this codebase keeps `Platform\Plans` (models `Plan`/`PlanFeature`, service `TenantEntitlements`) depending on `Platform\Tenancy` (the `Tenant` model, `tenancy()`/`tenant()` helpers) and never the other way around — `Platform\Plans` has zero knowledge of provisioning. `ensureDefaultPlanAssigned()` is the single exception: assigning a tenant's default plan is fundamentally a provisioning-*lifecycle* concern (matching `TenantProvisioner`'s existing responsibility for every other tenant-readiness step — database creation, filesystem, migration, seeding), not business logic that belongs to the plans domain itself. An event-listener-based alternative (Plans package listening for `Stancl\Tenancy\Events\TenantCreated`) was considered and rejected: it would fire on *every* `Tenant::create()` call across the whole test suite (all seven existing Platform test files create tenants in their fixtures), forcing every one of them to have a seeded default plan available merely to create a tenant row — an unwanted, surprising coupling for test files that have nothing to do with plans. Keeping assignment inside the explicit, opt-in `provision()` pipeline (which already needs a `PlatformIntegrationTestCase`-level plan-seeding fix regardless, see that class's docblock) keeps the blast radius contained to tests that actually provision tenants, which is every test that needs the tenant to be usable at all — the correct scope.

**C20. Platform Admin routes run under a dedicated `platform` middleware group (the framework's own `web` group minus `InitializeTenancyByDomain`), not the `web` group Bagisto's Shop/Admin routes use, and central-domain-only access is enforced by a dedicated `Platform\Admin\Http\Middleware\EnsureCentralDomain` check against `config('tenancy.central_domains')`, not by URL prefix alone.**
Why: `InitializeTenancyByDomain` is prepended to the `web` GROUP DEFINITION itself (TASK-ARCH-003/C-none, `bootstrap/app.php`), so any route using the `web` alias always attempts tenant resolution - for the central domain (`localhost`), that resolution has no matching `domains` row and throws `TenantCouldNotBeIdentifiedException`, mapped to a 404, exactly like an unknown tenant host (see docs/architecture/domain-routing.md, "Unresolved-domain handling"). Platform Admin therefore cannot use `web` at all. Rather than hand-maintain a second, separately-listed middleware array that could silently drift from `web`'s real contents over time, the `platform` group is *built* from `Middleware::getMiddlewareGroups()['web']` at boot time (after the `EncryptCookies` override and `InitializeTenancyByDomain` prepend already applied to `web`), filtered to remove only `InitializeTenancyByDomain` - it automatically tracks whatever `web` actually resolves to. This also gives a second, structural safety property "for free": since Platform Admin routes never run `InitializeTenancyByDomain`, no tenant database connection can ever become active while serving them, regardless of what Host header a request arrives with - the central-DB-safety requirement (docs/architecture/platform-admin.md item 12) is true by construction, not by discipline. `EnsureCentralDomain` (checked against the identical `central_domains` config `Stancl\Tenancy\Middleware\PreventAccessFromCentralDomains` already uses for the opposite direction) is the separate, explicit host-boundary enforcement the task brief required beyond URL-prefix alone - it 404s a tenant/unknown domain's request to `/platform/*` before it can reach any controller, view, or even the login form.

**C21. Platform Admin uses its own small, self-contained Blade layout (inline CSS, no build step) rather than reusing any Bagisto Admin visual component or layout.**
Why: the task brief explicitly required this NOT be decided "based purely on convenience," and named the real risk to avoid - future Bagisto Admin changes (`packages/Webkul/Admin`) silently breaking Platform Admin. Bagisto Admin's Blade layout is itself tightly coupled to its own Vite build (`packages/Webkul/Admin/src/Resources/assets`), its own Vue components, and its own `admin` guard/session assumptions - reusing any of it would mean Platform Admin inherits a maintenance dependency on a `packages/Webkul` package's internal structure, which is exactly the kind of coupling this whole project's "never modify/depend on Webkul internals" posture (C1/C8) is designed to prevent one layer up. A small, plain Blade layout with inline CSS (no asset pipeline, no npm/Vite dependency at all) costs little for this foundation task's scope (login, dashboard, two listings, one detail page) and can be replaced with something richer later without ever having depended on Bagisto Admin's assets in the first place.

**C22. `packages/Platform/Admin` is its own package (namespace `Platform\Admin`), depending on `Platform\Tenancy` and `Platform\Plans` (reads `Tenant`/`Plan`/`PlanFeature` directly); neither of those packages knows this package exists.**
Why: matches this project's established package-boundary convention (C11) one level further - Platform Admin is a distinct concern (central identity/routing/UI for managing the SaaS business) from both tenant lifecycle (`Platform\Tenancy`) and plan/entitlement data (`Platform\Plans`), and forcing either of those to import from `Platform\Admin` would create a cycle the moment `Platform\Tenancy`'s own `TenantProvisioner` needed anything UI/route-related. The dependency direction is one-way and enforced by simple absence: nothing in `packages/Platform/Tenancy` or `packages/Platform/Plans` references the `Platform\Admin` namespace anywhere.

**C23. `Platform\Plans` gains a small, feature-agnostic `TenantLimits` service (TASK-ARCH-012), but the actual products.limit wiring (hooking `Webkul\Product\Models\Product::creating`, counting root products) lives in a NEW, separate package, `Platform\Enforcement` - not inside `Platform\Plans` itself.**
Why: `Platform\Plans` has been completely free of any `Webkul\*` dependency since TASK-ARCH-008 (`Plan`/`PlanFeature`/`TenantEntitlements` know nothing about Bagisto's schema at all), which is what keeps it reusable/testable in isolation and keeps its central-connection-only architecture simple to reason about. Adding a direct `Webkul\Product` dependency into `Platform\Plans` to hook the `creating` event would break that purity for a concern (Bagisto-specific product counting) that has nothing to do with entitlement RESOLUTION. Instead, `TenantLimits` (the generic "is this usage still within the resolved limit" question - reusable for any future numeric limit) stays in `Platform\Plans`; the product-specific glue (the actual `Webkul\Product` model event listener, the exception-to-HTTP-response mapping) lives in the new `Platform\Enforcement` package, which depends on BOTH `Platform\Plans` and `Webkul\Product` - the one Platform package in this codebase deliberately allowed to know about a specific Webkul package, since gluing Bagisto's real extension points to the platform's own domain logic is its entire reason to exist. See docs/architecture/feature-limits.md "Package boundary and dependency direction".

**C24. `products.limit` counts only root/aggregate products (`products.parent_id IS NULL`), never configurable-product variants.**
Why: `products.parent_id` is a real, already-existing schema column distinguishing a configurable product's own row from each of its variant rows (`Webkul\Product\Type\Configurable::createVariant()`, which always sets `parent_id` explicitly) - no soft-delete column and no real `status`/`is_active` schema column exist on `products` at all (Bagisto's "status" is EAV custom-attribute data, not a real column), so those alternative counting semantics don't map cleanly onto the actual schema the way `parent_id IS NULL` does. This matches the task's own suggested "simplest stable interpretation: number of merchant-created Product aggregate/root records" exactly, and means a configurable product with any number of variants costs exactly one unit of the limit - consistent with how a merchant thinks about "how many products do I have," not an implementation detail of how Bagisto happens to store variant permutations.

**C25. Bulk product import enforcement (TASK-ARCH-012A, closing R39) hooks the import's VALIDATION phase (`AbstractImporter::validateData()`), not a per-batch hook near the actual `INSERT`.**
Why: product imports process as multiple, independent QUEUED JOBS (one per `import_batches` row) dispatched via `Bus::batch()`, which - per `Webkul\DataTransfer\Jobs\Import\ImportBatch`'s own docblock - "run side by side across the fleet," i.e. genuinely concurrently across however many queue workers are running. A check placed near the per-batch insert (the first extension point TASK-ARCH-012's own audit considered, then rejected as too costly to make correct) would have reproduced R38's TOCTOU race N-ways - two batches of the SAME import could each independently observe "still under the limit" and both proceed, since neither would see the other's in-flight insert. Validation, by contrast, always runs ONCE, synchronously, entirely BEFORE any batch job exists (confirmed live: Bagisto's product importer never opts into chunked/queued validation), and by the time it finishes every batch this import will ever have is already built and visible - so a single, whole-file check there gives genuinely atomic, all-or-nothing rejection: if it fails, `Import::isValid()` returns false and NO batch is ever dispatched, closing the bypass with a STRICTER guarantee than the single-creation (`Product::creating`) boundary TASK-ARCH-012 built has, rather than merely matching it.

**C26. The bulk-import check is wired via a plain subclass of Bagisto's product importer, swapped in through a targeted `config('importers.products.importer')` override - not an event listener, not a core modification.**
Why: `data_transfer.imports.validate.after` (a real, hookable event wrapping the whole validation pass) was considered first, but only passes the bare `Import` record to listeners - not the importer instance or its `errorHelper`, both of which the check needs direct access to (to read already-materialized batch rows and to attach per-row errors that make `Import::isValid()` correctly return false). A subclass gets that access naturally via inherited `protected` properties, with zero `packages/Webkul` modification: `Webkul\DataTransfer\Helpers\Import::getTypeImporter()` resolves the importer purely by class name read from config, so `EnforcingProductImporter` is entirely invisible to the rest of `packages/Webkul/DataTransfer` - remove the config override and behavior reverts to stock Bagisto exactly. This is the same "importer override/binding" extension shape the task's own instructions explicitly named as an acceptable option, applied literally.

**C27. Tenant suspension enforcement (TASK-ARCH-013) is a dedicated `web`-group HTTP middleware (`Platform\Tenancy\Http\Middleware\BlockSuspendedTenants`) that re-resolves the tenant via stancl's own `DomainTenantResolver`, rather than a listener on `Stancl\Tenancy\Events\InitializingTenancy`.**
Why: the event-listener approach was the first, more "elegant"-looking design (no duplicate resolver call, hooks directly into `Tenancy::initialize()` before its bootstrappers run) - but it is wrong: `InitializingTenancy` fires identically for a real inbound HTTP request AND for Platform Admin's own trusted internal `$tenant->run()` calls (`TenantProvisioner::remigrate()`/`platform.tenants.migrate-pending` most concretely, whose own established contract from TASK-ARCH-010/R33 explicitly promises "safe to run against any tenant, any number of times, regardless of status"). A listener on that event cannot distinguish the two call sites - both invoke the identical `Tenancy::initialize()` method - so it would have silently broken an already-approved, already-tested Platform Admin action the very first time someone tried to run pending migrations against a suspended tenant. A middleware, scoped to the `web` HTTP middleware group only, structurally excludes every internal `$tenant->run()` call (none of them pass through any HTTP middleware pipeline at all), closing this gap by construction rather than by a runtime check that could be gotten wrong. The cost - the domain resolves twice per non-suspended request (once in this middleware, once again in `InitializeTenancyByDomain` moments later) - is a cheap, central-only, indexed query, and reuses stancl's own `DomainTenantResolver` class unmodified rather than inventing a second, competing resolver.

**C28. Suspended-tenant responses use `423 Locked`, not `403 Forbidden` or `503 Service Unavailable`.**
Why: 403 already carries an established, different meaning in this codebase - `Webkul\Core\Exceptions\Handler` uses it for genuine in-store authorization failures (a signed-in user lacking a specific permission); reusing it for "the entire tenant is administratively locked" would blur two meaningfully different failure classes behind the same status code. 503 implies a temporary infrastructure/availability problem, not a deliberate, reversible platform action. 423 precisely communicates "this resource exists, you are not being denied for who you are, but it is currently administratively locked and may become available again" - the exact semantic this feature needs, and a status code no Bagisto code path already claims a conflicting meaning for.

**C29. `Platform\Tenancy\Services\TenantLifecycle` is a plain, request/session-independent service class (not a controller-embedded set of methods), even though only one caller (`Platform\Admin\Http\Controllers\TenantController`) exists today.**
Why: the task brief explicitly anticipates a future billing-driven automation needing the identical operation ("subscription delinquent -> suspend()", "payment recovered -> reactivate()") with no HTTP request in the loop at all. Designing the service with zero HTTP/session coupling now costs nothing and avoids a rework later - mirrors the same reasoning that already led `TenantProvisioner` (TASK-ARCH-002) to be a plain service rather than controller logic.

**C30. Non-Ready, non-Suspended tenant statuses (TASK-ARCH-014: `Pending`, `Provisioning`, `Failed`, `Deleting`, `Deleted`, and any future/unrecognized status) return `503 Service Unavailable`, a distinct code from `Suspended`'s established `423 Locked`.**
Why: 423 (C28) specifically communicates "administratively locked, reversible, not a permissions issue" - an explicit platform action taken against an otherwise-working tenant. None of the other non-Ready statuses fit that meaning: `Pending`/`Provisioning` mean "not yet available," `Failed` means "not currently in a working state," `Deleting`/`Deleted` mean "on the way out" - all are "not currently servable for infrastructure/lifecycle reasons," which is exactly 503's standard HTTP semantic, not an administrative lock. Reusing 423 for all of them would blur a genuinely different failure class behind one status code; inventing a third, bespoke code for this set would add complexity with no real benefit over the existing standard code that already fits. This was flagged as the likely direction in RISK_REGISTER.md R41 before TASK-ARCH-014 started and is now confirmed as the implementation.

**C31. `Platform\Tenancy\Http\Middleware\BlockSuspendedTenants` (TASK-ARCH-013) is generalized IN PLACE into `Platform\Tenancy\Http\Middleware\TenantAccessGate` (TASK-ARCH-014) - not left alongside a second, new middleware class.**
Why: both classes solve the identical structural problem (resolve the tenant centrally, before any tenant DB connection, and decide whether this specific request may proceed) for an overlapping input domain (`TenantStatus`) - `TenantAccessGate`'s `Suspended` branch is a byte-for-byte behavioral continuation of `BlockSuspendedTenants` (identical 423 response, identical `tenancy::suspended` view, unchanged). Keeping two separate middleware entries doing status-based gating in the same `web`-group priority slot would require reasoning about their relative order and combined effect on every request, for no benefit - one gate, one fail-closed `match` over the full enum, is strictly simpler to audit and cannot itself introduce an ordering bug between two gates. The class rename (rather than keeping the old, now-inaccurate name) reflects that its responsibility genuinely broadened from "block one specific status" to "decide readiness for every status."

**C32. A plan's `code` is settable only at creation and is never accepted by the update action - immutable for the lifetime of the plan (TASK-ARCH-015).**
Why: investigated before deciding, per this task's explicit instruction to prefer immutability "unless the current architecture provides a strong reason otherwise" - no such reason was found; the opposite was found instead. `code` is a stable, environment-wide business identifier: `Platform\Tenancy\Services\TenantProvisioner::ensureDefaultPlanAssigned()` resolves the default plan by `code` from `config('platform.plans.default_code')` (an `.env`-driven value, `PLATFORM_DEFAULT_PLAN_CODE`), and `tests/Feature/Platform/TenantEntitlementsTest.php` also resolves a plan by `code` directly. Making `code` editable would let an operator silently invalidate either reference (provisioning already fails loudly rather than silently in that case - see C-none/`ensureDefaultPlanAssigned`'s own docblock - but it is still an entirely avoidable operational footgun with zero present use case motivating the risk). `name`/`description`/`sort_order`/`is_active` remain fully editable - only the stable identifier is frozen.

**C33. Deactivating a plan (`is_active = false`) means "not available for new/manual assignment," never "stop existing tenants" - and there is no hard delete for a plan (TASK-ARCH-015).**
Why: matches the task's own explicit instruction and the existing schema's own constraint (`plans.id` is `restrictOnDelete()`-referenced from `tenants.plan_id`, so a hard delete of an in-use plan was never simple regardless). `is_active` is consulted in exactly one place in the whole codebase, `Platform\Plans\Services\TenantPlanAssignment::assign()` (the gate on NEW/manual assignment) - `TenantEntitlements`/`TenantLimits` never check it, so a tenant already on a deactivated plan keeps resolving real entitlements from it indefinitely, with no suspension, no `tenants.plan_id` change, no tenant database touched, and no automatic migration to a different plan. This mirrors the same "deactivation, not deletion" pattern C-none (TASK-ARCH-013's `TenantLifecycle`) already established for tenant suspension - a reversible, non-destructive administrative state, not data loss.

**C34. `Platform\Plans\Services\PlanSeeder::seed()` switched from `updateOrCreate()` to `firstOrCreate()` throughout (TASK-ARCH-015).**
Why: before TASK-ARCH-015, Platform Admin had no CRUD for plans/features at all, so nothing could ever diverge from `PlanSeeder`'s hardcoded FREE/BASIC/PRO definitions - `updateOrCreate()`'s "always sync to this definition" behavior was harmless by construction. Once Platform Admin CRUD exists, that behavior becomes actively destructive: re-running `platform:plans:seed` (a routine, documented, idempotent-by-design bootstrap command) after a platform admin edits a plan's name/description/sort_order/active flag (or a feature's type/value) would silently revert those edits back to the hardcoded illustrative data on every re-run - an unexpected, undocumented configuration reset disguised as a harmless bootstrap step. `firstOrCreate()` preserves the actually-needed properties (creates a plan/feature if its natural key doesn't exist yet; introduces any brand-new illustrative feature a future code change adds) while never touching an already-existing row's current values, no matter what they are. Proven live: `tests/Feature/Platform/PlatformPlanManagementTest.php` ("PlanSeeder does not overwrite operator-managed edits on re-run").

**C35. `plan_features`'s duplicate-`feature_code`-per-plan invariant needed no new migration - the database-level half already existed (TASK-ARCH-008's `unique(['plan_id', 'feature_code'])`), only the application-level half (a clean validation error, not a raw `QueryException`) was missing (TASK-ARCH-015).**
Why: investigated before implementing, per this task's own explicit instruction to check whether the invariant was "currently enforced by schema or only convention" before assuming a migration was needed. It was already schema-enforced. Rather than a redundant migration, `Platform\Admin\Http\Controllers\PlanFeatureController::store()` adds a scoped `Rule::unique` (connection-qualified against `PlanFeature`'s own `CentralConnection` - see C-none/RISK_REGISTER.md R42 for why that qualification matters) so a duplicate attempt fails as an ordinary form validation error, with the pre-existing database constraint remaining as the structural, always-correct backstop.

**C36. Production cache store is Redis - RESOLVED, no longer a pending human decision (TASK-ARCH-015B).**
Why: `CACHE_STORE=redis` in `.env.example` (in place since TASK-ARCH-004's R15 fix, with an inline comment already calling it "the production recommendation") is now explicitly accepted as the decided production cache architecture, closing the item previously listed under "HUMAN DECISION REQUIRED." This resolves only the CHOICE of cache store/`stancl/tenancy` cache-tenancy bootstrapping for the application layer - it does **not** mean Redis infrastructure is provisioned anywhere by this repository; standing up/operating a real Redis instance remains a Phase 18 (Production Deployment) infrastructure concern, unchanged. Separately and NOT resolved by this decision: `RESPONSE_CACHE_ENABLED` (Bagisto's full-page response cache, a distinct mechanism from ordinary `Cache::`-facade isolation) stays `false` by default in `.env.example` - see C15, unchanged and reaffirmed, not superseded by this entry. `.env.example`'s own inline comments now state both points explicitly, so this decision and its boundary are documented at the point of use, not only here.

**C37. `Platform\Subscriptions` is a new, dedicated package, not folded into `Platform\Plans` or `Platform\Tenancy` (TASK-ARCH-016).**
Why: matches this project's established one-concern-per-package convention (C11, extended by C23's `Platform\Enforcement` precedent) - "what entitlements does this tenant get" (`Platform\Plans`) and "what is this tenant's billing lifecycle state" (`Platform\Subscriptions`) are genuinely distinct concerns that happen to compose on the same admin page, not one concern. Dependency direction: `Platform\Subscriptions -> Platform\Plans -> Platform\Tenancy`. Two narrow, deliberate exceptions to "neither Plans nor Tenancy depends back" exist, both justified identically to C19's own precedent: `TenantProvisioner::ensureInitialSubscriptionStarted()` (a provisioning-lifecycle concern, not business logic Subscriptions needs to know about) and `Plans\Http\Controllers\Admin\MyPlanController` (a narrow, read-only display dependency, the same "controller reads another package's `CentralConnection` model directly" pattern already used elsewhere, e.g. `Platform\Admin`'s own controllers reading `Plan`/`Tenant`). A narrow interface/abstraction was considered for the `MyPlanController` case (task section 25's option B) and rejected as inconsistent ceremony - this codebase has no precedent of introducing an interface just to read another package's central model for display.

**C38. `subscriptions.status` is a plain string column, `SubscriptionStatus` deliberately excludes `past_due` (TASK-ARCH-016).**
Why: matches `plan_features.type`'s already-established precedent (enum-cast at the Eloquent level for a closed, fully-controlled set of values; a plain string at the schema level so a new case never needs a migration). `past_due` specifically was evaluated and excluded: detecting "a payment failed" fundamentally requires a payment-provider signal (webhook/reconciliation) that doesn't exist anywhere in this codebase - adding the enum case now, with nothing that could ever transition into it, would be exactly the kind of speculative unused surface this project avoids (per the task's own explicit instruction not to add statuses "simply because Stripe has them").

**C39. Subscription lifecycle mutations always call `TenantPlanAssignment` internally rather than writing `tenants.plan_id` a second, independent way (TASK-ARCH-016).**
Why: this is the concrete mechanism that makes C18's finalized Option C true by construction - `SubscriptionLifecycle::start()`/`startTrial()`/`changePlan()` all delegate the "is this plan assignable, then assign it" question to the exact same `TenantPlanAssignment::assign()` TASK-ARCH-015's Platform Admin manual assignment already used, so provisioning-time and subscription-driven plan changes can never silently disagree about what "assignable" means, and `subscription.plan_id == tenant.plan_id` holds after every mutation without a separately-written synchronization step that could be forgotten in one call site.

**C40. `TenantStatus` and `SubscriptionStatus` are two fully independent state machines with zero automatic coupling between them (TASK-ARCH-016).**
Why: the task brief was explicit that this boundary must hold (`TenantStatus = Ready` + `SubscriptionStatus = Canceled` is a valid, unremarkable state) and must not be silently violated by convenience code (e.g. "canceling a subscription automatically suspends the tenant"). `Platform\Subscriptions\Services\SubscriptionLifecycle` never reads or writes `$tenant->status`; nothing in `Platform\Tenancy` ever reads or writes a `Subscription`. This mirrors the exact reasoning `docs/architecture/subscriptions.md`'s own Phase-0 sketch already anticipated ("intentionally independent from the tenant-provisioning state machine") - TASK-ARCH-016 confirms and implements that boundary rather than revising it. A future, explicit billing-policy task may orchestrate both services together (e.g. "subscription delinquent for N days -> suspend the tenant"); this task deliberately builds no such coupling, hidden or otherwise.

**C41. `SubscriptionBackfill` bypasses `TenantPlanAssignment`'s active-plan gate - the one deliberate exception in the whole Subscription domain (TASK-ARCH-016).**
Why: every other write path in this domain reuses `TenantPlanAssignment::assign()` (C39) specifically to enforce "only an active plan may be newly assigned" - but backfill is not a new assignment decision, it is recording an already-existing historical fact (`tenants.plan_id` already holds this value, for tenants that predate this task). Routing backfill through the active-only gate would mean a tenant whose plan happened to be deactivated between TASK-ARCH-015 and TASK-ARCH-016 gets silently skipped or errored during backfill - exactly the "deactivation must never disturb an existing assignment" rule C33 already established, violated via a different code path. Writing the `Subscription` row directly for backfill avoids that. See `Platform\Subscriptions\Services\SubscriptionBackfill`'s own docblock.

**C42. `Platform\Billing` is a new, dedicated package (TASK-ARCH-018). Dependency direction: `Platform\Billing -> Platform\Subscriptions -> Platform\Plans -> Platform\Tenancy`.**
Why: matches C37's own precedent - "how does this tenant pay" (Billing) is a genuinely distinct concern from "what is this tenant's lifecycle state" (Subscriptions), even though Billing will eventually call into Subscriptions. `Platform\Subscriptions` remains completely unaware `Platform\Billing` exists - no class in that package imports anything from this one, and this task did not add any exception to that rule (unlike C37's own two narrow Plans/Tenancy exceptions - Billing needed none in this task, since no checkout/webhook flow yet calls `SubscriptionLifecycle`). `Platform\Plans\Models\Plan` was deliberately NOT given a `prices()` relation into `Platform\Billing\Models\PlanPrice` - that would create a reverse dependency (Plans -> Billing) alongside the already-established forward one (Billing -> Plans), a real cycle. `PlanPrice` rows are queried by `plan_id` directly wherever needed instead (see `Platform\Admin\Http\Controllers\PlanController::show()`).

**C43. `Platform\Billing\Adapters\StripePaymentProvider` uses `stripe/stripe-php` (the raw SDK) directly, not `laravel/cashier` (TASK-ARCH-018).**
Why: `laravel/cashier` owns its own Stripe-shaped `Subscription`/`Customer` model concepts and database schema conventions - adopting it would mean either running two parallel, potentially-conflicting "Subscription" concepts (Cashier's and this codebase's own provider-neutral `Platform\Subscriptions\Models\Subscription`, TASK-ARCH-016) or contorting Cashier to defer to ours, fighting the package rather than using it as intended. The raw SDK behind our own `PaymentProvider` contract has no such ownership assumptions - it is a pure HTTP-API client, exactly the shape a provider-neutral adapter needs. `laravel/cashier` remains an unused `composer.json` dependency, unchanged from C-none/`docs/architecture/billing.md`'s original Phase 0 note.

**C44. Plan pricing lives in a separate `plan_prices` table, not `price_monthly`/`price_yearly` columns on `Plan` itself (TASK-ARCH-018).**
Why: a fixed pair of columns can only ever represent exactly two intervals; this platform's own task brief explicitly anticipates needing to support arbitrary future billing cycles cleanly. A separate table with `billing_interval`/`interval_count` columns extends to a third/fourth interval (e.g. "every 3 months") with a data change, not a schema migration and matching code change at every read site. `Plan` itself gains zero new columns - `plans` stays exactly as entitlement-focused as C-TASK-ARCH-008/015 originally scoped it.

**C45. `Payment.amount_minor`/`Payment.currency` are a historical snapshot, copied at creation time and never re-derived from `plan_price_id` afterward (TASK-ARCH-018).**
Why: a `PlanPrice`'s amount can change after a `Payment` referencing it already exists (a price increase, a currency change) - if `Payment`'s own money fields were computed via a live join to `plan_prices` instead of stored directly, editing a price would silently rewrite what every historical payment against it appears to have charged, an obviously wrong outcome for anything resembling a financial record. `plan_price_id`'s `nullOnDelete()` reinforces this: even if the `PlanPrice` row is later deleted entirely, the `Payment`'s own `amount_minor`/`currency` remain intact and authoritative - `plan_price_id` is traceability metadata only, never the source of truth for what a payment attempt actually charged.

**C46. `PaymentStatus` is deliberately minimal (`Pending`/`RequiresAction`/`Succeeded`/`Failed`/`Canceled`/`Refunded`) - not a mirror of Stripe's complete `PaymentIntent` status set (TASK-ARCH-018).**
Why: matches C38's own precedent for `SubscriptionStatus` exactly - only states this platform has real, exercised semantics for. Stripe's `requires_payment_method`/`requires_confirmation`/`processing`/`requires_capture` all collapse to this platform's own `Pending` (see `StripePaymentProvider::mapStatus()`'s documented mapping) rather than being reproduced 1:1, since nothing in this codebase needs to distinguish between them - a future provider with a completely different status vocabulary maps onto the same small, meaningful set without forcing this enum to grow to accommodate it.

**C47. Stripe Checkout Session is created in `mode: 'payment'`, never `mode: 'subscription'` (TASK-ARCH-019).**
Why: Stripe's own `subscription` mode creates a Stripe-owned `Subscription`/`Customer` object pair - using it would make Stripe a SECOND subscription-lifecycle source of truth alongside `Platform\Subscriptions\Models\Subscription`, exactly the conflict C43 already rejected `laravel/cashier` over. `payment` mode creates only a one-off payment; Stripe never learns this platform has a "subscription" concept at all. `Platform\Subscriptions` remains the sole lifecycle source of truth - Billing only ever calls `SubscriptionLifecycle::changePlan()` after its OWN webhook processing decides to, never because Stripe told it a subscription changed.

**C48. Webhook signature verification is a SEPARATE contract, `Platform\Billing\Contracts\WebhookVerifier`, not a method on `PaymentProvider` (TASK-ARCH-019, task section 26).**
Why: not every future provider shares Stripe's signature-header concept - a bank adapter might use a signed callback, polling, or server-to-server verification with a completely different event format (task section 26's own examples). Putting signature verification on the shared `PaymentProvider` interface would force every future adapter to implement a method that may not even make sense for it. `Platform\Billing\Http\Controllers\StripeWebhookController` deliberately type-hints `StripeWebhookVerifier` directly (not the generic contract) - its own route/header-extraction logic is already Stripe-specific from the first line; a future bank adapter gets its own dedicated controller/route, never a shared dynamic dispatch.

**C49. `WebhookEventProcessor` wraps the ENTIRE event-processing sequence - reading/creating the `BillingProviderEvent` row, resolving the `Payment`, `PaymentLifecycle`, and `SubscriptionLifecycle::changePlan()` - inside ONE `DB::transaction()` (TASK-ARCH-019, task section 16).**
Why: this is what makes "processing crashes after receiving but before completion" (task section 15) safe without any bespoke intermediate-state tracking. A crash anywhere inside the transaction rolls back everything (MySQL/InnoDB atomicity), so there is no durably-observable "Payment succeeded but plan not yet changed" state - a retry always re-enters from a clean `Received`-or-nonexistent row. The alternative (three separately-committed steps) would require inventing extra state to detect and safely resume from a partial commit; the transaction makes that whole problem disappear.

**C50. Checkout double-click idempotency reuses the tenant's existing Pending `Payment` for the same `(tenant, plan_price)` pair rather than creating a second row (TASK-ARCH-019, task section 21).**
Why: the simplest rule that prevents duplicate financial records without any payment-intent-orchestration machinery (explicitly rejected by the task's own "do not over-engineer" instruction). A Payment already in a TERMINAL state (Succeeded/Failed/Canceled/RequiresAction) for the same pair does NOT block a new attempt - a fresh Payment row is created, matching `SubscriptionLifecycle::start()`'s own "restart in place only from a terminal state" precedent (C-none, TASK-ARCH-016).

**C51. The Stripe webhook endpoint uses a dedicated CSRF-exempt path, `billing/webhook/*`, never reusing the pre-existing `stripe/*` exemption (TASK-ARCH-019).**
Why: `stripe/*` was already CSRF-exempted in `bootstrap/app.php` before this engagement began, for `packages/Webkul/Stripe`'s own, unrelated storefront-order-payment webhook (a tenant-scoped Bagisto core package, untouched by this whole engagement). Reusing that prefix for Platform Billing's central-only webhook would risk a route collision and conflate two genuinely separate integrations under one exemption rule. A second, clearly-named exemption entry keeps the two systems' CSRF/route boundaries independent and easy to reason about separately.

**C52. `Platform\Signup` is a new, dedicated package depending ONLY on `Platform\Tenancy` (TASK-MVP-001).**
Why: matches the C11/C22/C37/C42 one-concern-per-package precedent exactly - public merchant signup is a distinct concern from tenant lifecycle itself, and `Platform\Tenancy` (like `Platform\Plans`/`Platform\Subscriptions` before it) should stay free of any public HTTP/UI surface. No dependency on `Platform\Plans`/`Platform\Subscriptions`/`Platform\Billing`/`Platform\Admin` was needed - `TenantProvisioner::provision()` already encapsulates default-plan lookup and subscription start internally, so Signup never touches those packages directly.

**C53. `TenantProvisioner::provision()` gained an optional, additive `$ownerAdmin` parameter rather than `Platform\Signup` performing a separate post-provision write of its own (TASK-MVP-001, approved plan decision 1).**
Why: owner-admin identity is a genuine provisioning-READINESS concern (matching this class's existing responsibility for every other tenant-readiness step), not business logic that belongs one layer up - and critically, making it a real pipeline step (not a bolt-on side call) is what makes it correctly retry-safe: a resumed/retried `provision()` call always re-reaches the owner-admin step, exactly like every other `ensure*()` step. Every existing caller (`tenant:provision` CLI, Platform Admin's provision/retry action) passes nothing and is completely unaffected - confirmed no behavior change for either.

**C54. The tenant `id` IS the merchant-chosen "store address" slug - no separate slug column (TASK-MVP-001).**
Why: every existing fixture and CLI usage in this codebase already treats `id` as a human-chosen string (`tenant-a`, `tenant-planmgmt-a`, ...), never a UUID in practice, despite `config('tenancy.id_generator')` defaulting to `Stancl\Tenancy\UUIDGenerator` (only ever a fallback for when `id` isn't explicitly supplied). Introducing a second, separate slug concept would create two competing identifiers for the same subdomain with no present use case. The validation this requires (character allowlist, length, reserved words, uniqueness) is exactly what closes R19 at the same time.

**C55. Retry authorization is a cryptographically signed, time-limited URL (Laravel's own `signed` route middleware), never "knowledge of the tenant id/slug" - and the plaintext password is never persisted anywhere, including session (TASK-MVP-001, required security adjustment to the approved plan).**
Why: the tenant slug/domain is public information (it becomes the merchant's own storefront address) and must not double as an authorization credential. A signed URL is unguessable and tamper-evident without requiring any new central merchant-authentication system (explicitly ruled out). Because the owner-admin provisioning step needs a plaintext password and plaintext passwords must never be written to `tenants`/`data`/cache/logs/session (session storage was considered and rejected too - `SESSION_DRIVER=database` in this project's real `.env` makes a session write a real persistence operation, not an in-memory-only one), a failed attempt has nothing to silently resume with: the retry flow always asks the merchant to re-enter their password. `TenantProvisioner::provision()`'s pre-existing `if (status === Ready) return;` early return is what makes a stale/leaked/reused signed link against an already-Ready tenant a safe no-op by construction, not an additional check bolted on for this task.

**C56. `Platform\Signup` duplicates a small `EnsureCentralDomain` middleware rather than depending on `Platform\Admin`'s existing one (TASK-MVP-001).**
Why: the approved plan explicitly required keeping `Platform\Signup` dependent only on `Platform\Tenancy` unless another dependency proved genuinely required - importing `Platform\Admin`'s copy would create a new, backwards-feeling dependency edge (a lower-level tenant-creation concern depending on a higher-level operational-panel package nothing else depends on) for seven lines of logic that read one shared config key and are unlikely to drift. If a third consumer of this exact check ever appears, that is the point to consolidate it into `Platform\Tenancy` (its more natural home) - not done now, to avoid touching an already-approved package's file layout for this task.

**C57. `channels.hostname` is written as a bare hostname (no scheme), never `http://`/`https://`-prefixed, and only ever `channels.id = 1`'s row (TASK-MVP-003).**
Why: verified directly from Bagisto source rather than assumed. The Admin "Host Name" field validates with a plain `unique:channels,hostname` rule (no `url:` rule); `Webkul\Core\Core::getCurrentChannel()`'s own hostname lookup explicitly checks the bare form as a first-class candidate value; and both real consumers of this field (`SitemapController::channelBaseUrl()`, `ProcessSitemap::channelBaseUrl()`) already normalize a schemeless value to `https://` themselves before using it. Writing a scheme here would hardcode a decision (local dev currently serves tenants over plain `http://`) this provisioning step has no business making - correctly deferred to read time and to TASK-MVP-004's eventual real production scheme decision. Targeting only `id=1`'s `hostname` column (never any other channel field) means a merchant's own locale/currency/theme/design configuration is never disturbed by this step, on first provisioning or on repeat.

**C58. `platform:tenants:repair-channel-hostname` is a new, narrowly-scoped command, not folded into `platform:tenants:migrate-pending` (TASK-MVP-003).**
Why: mirrors that command's exact shape (`--tenant=*` option, same reporting style) since both are "repair an already-provisioned tenant for a fix that postdates its own provisioning" commands, but deliberately kept separate per the task's own explicit "do not create a broad repair-everything command" instruction - each addresses one specific, unrelated correctness issue. Unlike `migrate-pending` (safe against a tenant with no physical database at all, since Laravel's own migration tracking handles that gracefully), this command only processes `Ready` tenants, clearly skipping (never erroring on) any other status - a Pending/Provisioning/Failed tenant has no reliable guarantee its `channels` table exists yet, and `TenantProvisioner::provision()` already applies the same fix correctly once such a tenant successfully reaches Ready.

**C59. `Platform\Signup\Http\Middleware\FlagFirstLoginWelcome` is registered as an ordinary `web`-group middleware member (`bootstrap/app.php`), not attached to a single named route the way TASK-ARCH-005/R25's `attachTenancyToImageCacheRoute()` attaches to `imagecache` (TASK-MVP-003).**
Why: the R25-style approach was attempted first (byte-for-byte the same `$this->app->booted(fn () => $router->getRoutes()->getByName(...)->middleware([...]))` pattern) and empirically found not to work for `admin.session.create` specifically - real debug logging (both `artisan tinker` and an actual failing Pest run) confirmed this route genuinely does not exist yet in the router's collection at the moment any `booted()` callback fires in this application, even though `AdminServiceProvider::boot()` registers it via a plain, unconditional, synchronous `require` with no lazy loading anywhere in that chain - while the identical mechanism, checked side-by-side, still works correctly for `imagecache`. The exact root cause was not fully isolated (see RISK_REGISTER.md R50 - a genuine, narrow gap in this project's own understanding of its own bootstrap sequence, not swept under the rug). The working alternative needs no such timing assumption: the middleware is appended to `web` (the same, already-established extension point TASK-ARCH-003 used for `InitializeTenancyByDomain`), with `Request::routeIs('admin.session.create')` doing the narrow targeting at request time instead of at route-registration time.

**C60. Per-tenant timezone remains out of scope permanently, not deferred pending a future Platform task (TASK-MVP-003).**
Why: investigated and confirmed a genuine Bagisto architectural characteristic - `config('app.timezone')` is a single, process-wide value with no per-tenant/per-channel override anywhere in Bagisto's own config surface, and closing it would require adding tenant-aware timezone resolution to Bagisto's own date/time handling, a `packages/Webkul` core change this project's standing rule does not permit. Documented as a known, accepted MVP limitation rather than a backlog item - revisit only if a future task's own brief explicitly authorizes Bagisto core extension work for this specific purpose.

**C61. `PLATFORM_CENTRAL_DOMAINS` is a new, explicit env source for `config('tenancy.central_domains')`, deliberately never derived from `config('platform.base_domain')` (TASK-MVP-004A).**
Why: the two configuration values answer genuinely different questions - `PLATFORM_BASE_DOMAIN` is the parent hostname tenant subdomains attach to; `PLATFORM_CENTRAL_DOMAINS` is which hostname(s) serve the central app (Platform Admin, signup). A real deployment could legitimately run its central app on the exact same host tenants are subdomained under, or on an entirely different one - only the operator knows which. Deriving one from the other would silently pick a topology nobody chose. `127.0.0.1`/`localhost` remain always-included local-dev defaults regardless of this env var, so local development needs zero additional setup - see `tests/Feature/Platform/CentralDomainConfigurationTest.php`.

**C62. `QUEUE_CONNECTION=sync` is the recommended posture through the initial pilot; no queue worker is deployed as part of TASK-MVP-004A or its recommended TASK-MVP-004B bootstrap (TASK-MVP-004A investigation, formalized here).**
Why: under `sync`, every queued job (including order-confirmation mail) runs inline within the same HTTP request - no separate worker process to supervise, restart after deploy, or lose jobs from. TASK-ARCH-006 already proved the async (`redis`) path is tenant-isolated and correct if pilot volume/responsiveness later demands it, so this is a scale decision to revisit with evidence, not an architecture gap today.

**C63. `SESSION_DRIVER=database` is confirmed, not revisited, for production too (TASK-MVP-004A investigation, formalized here).**
Why: it is the already-proven, already-tested architecture (tenant sessions in each tenant's own database, Platform Admin sessions in the central database, both real isolated `sessions` tables, zero extra isolation code). No concrete problem was found that would justify moving to Redis-backed sessions merely because Redis is already required for cache (C36) - that would add a new isolation mechanism (`RedisTenancyBootstrapper`, currently disabled, never exercised anywhere in this codebase) to solve a problem that does not exist.

**C64. `CACHE_STORE=redis` is confirmed MANDATORY (not merely recommended) for production (TASK-MVP-004A investigation, formalized here).**
Why: `CacheTenancyBootstrapper` (C36, always active) requires a taggable store - `array` is safe (no cross-tenant leak) but provides no real cross-request caching benefit under PHP-FPM, since each worker process has its own private, empty array. A real, running Redis instance is required for the cache layer to do anything useful in production, independent of whether an async queue connection is ever adopted (C62).

**C65. `Platform\Billing\Http\Controllers\Tenant\CheckoutController::store()`'s `MissingProviderCredentialsException` is handled via a global `bootstrap/app.php` exception-render callback, not a try/catch inside the controller method (TASK-MVP-004A).**
Why: structurally the only option available - `CheckoutService` (which constructor-injects the `PaymentProvider` contract, whose resolution is what throws) is METHOD-injected into `store()`, so Laravel resolves it - and the exception can fire - during the controller's own method-dependency resolution, before `store()`'s method body (and any try/catch inside it) ever runs. Confirmed structurally via `tests/Feature/Platform/CheckoutBillingUnavailableTest.php` test 6 (reflection on the method signature + a direct `app(CheckoutService::class)` resolution). The fix reuses the exact mechanism `bootstrap/app.php` already uses for `TenantCouldNotBeIdentifiedException`, requiring zero change to `Platform\Billing`'s existing "fail loudly at resolution time" adapter design (`StripePaymentProvider`'s own docblock) and zero change to subscription/payment lifecycle semantics - by the time the exception fires, no Payment row could have been created regardless, since `CheckoutService::initiate()` itself was never reached.

**C66. An unresolved-Host-header failure is now intercepted via stancl/tenancy's own `InitializeTenancyByDomain::$onFail` hook, not a Laravel exception-handler registration or a new wrapping middleware (TASK-MVP-004B, RISK_REGISTER.md R53).**
Why: `bootstrap/app.php` already had a `$exceptions->render(TenantCouldNotBeIdentifiedException::class, ...)` registration that should have produced a clean 404, but under `APP_DEBUG=false` (the real production value, never previously tested) it silently lost a registration-order race against `Webkul\Core\Exceptions\Handler`'s own catch-all `Throwable` renderable - confirmed by reading the actual `Illuminate\Foundation\Exceptions\Handler`/`ApplicationBuilder` vendor source, not assumed. Two fixes were considered: (a) a new Platform-owned middleware wrapping `InitializeTenancyByDomain` in a try/catch, mirroring `TenantAccessGate`'s own pattern; (b) setting `InitializeTenancyByDomain::$onFail`, a static property `Stancl\Tenancy\Middleware\IdentificationMiddleware::initializeTenancy()` already checks and calls on exactly this failure, defaulting to `fn ($e) => throw $e` when unset. (b) was chosen - it intercepts the exception at its actual throw site, needs no new middleware class or `bootstrap/app.php` ordering to reason about, and is a supported, documented stancl/tenancy extension point rather than a second competing catch mechanism. The pre-existing `bootstrap/app.php` render registration is kept as a defense-in-depth fallback for any path that might still reach the exception-handler pipeline directly, but is dead code for the normal 'web' HTTP path now.

**C67. Platform-owned middleware that rejects a request on a host/domain check returns the response directly instead of throwing (TASK-MVP-004B, RISK_REGISTER.md R54).**
Why: `Platform\Admin\Http\Middleware\EnsureCentralDomain` and its deliberate duplicate in `Platform\Signup` both used to `throw new NotFoundHttpException`, relying on Laravel's exception-handler pipeline to render it - which, under `APP_DEBUG=false`, rendered via Bagisto's own `handleHttpException()` catch-all, falling back to a view (`shop::errors.index`) that needs tenant-scoped tables absent on the central connection these rejected requests never leave, producing a raw 500 (the same failure family as C66/R53). Since both middleware classes are fully Platform-owned (unlike R53's stancl-vendor-thrown exception), there was no need to intercept anything thrown into the pipeline at all - returning `response()->json(['message' => 'Not Found'], 404)` directly sidesteps the pipeline, and Bagisto's own catch-all, entirely.

**C68. `Request::HEADER_X_FORWARDED_HOST` is no longer trusted in `bootstrap/app.php` (TASK-MVP-004B, RISK_REGISTER.md R55) - Host resolution relies solely on the raw `Host` header.**
Why: found live while investigating R54 - trusting `X-Forwarded-Host` from the configured trusted-proxy IP let a client spoof `$request->getHost()` to an arbitrary value, because `mod_proxy_http` merges (comma-appends) its own detected real host onto any client-supplied `X-Forwarded-Host` rather than replacing it, and Symfony's trusted-header resolution reads the client-supplied (first) entry of that merged list. An Apache-layer fix (`RequestHeader set X-Forwarded-Host "%{Host}i"`, overwriting the header with Apache's own vhost-matched value) was attempted first but abandoned - the format-string interpolation did not evaluate as documented on this server's Apache/mod_headers build, and `mod_expr` (needed for the modern `expr=` alternative) is not loaded. Given the real production reverse-proxy config always sets `ProxyPreserveHost On`, the raw `Host` header Laravel receives is already exactly what Apache's own vhost matched the request against - immune to spoofing by construction, and sufficient on its own for this single-hop topology. Not trusting `X-Forwarded-Host` at all is therefore both simpler than fixing the Apache-side rewrite and strictly safer. `X-Forwarded-For`/`Proto`/`Port` remain trusted, since none of them can influence which vhost/tenant a request resolves to.

**C69. `config/database.php`'s `tenant_provisioning` connection no longer sets a default `database` at all (TASK-MVP-004B, RISK_REGISTER.md R56).**
Why: found live on the real pilot server's first-ever production merchant signup - the correctly-scoped `estore_provisioner` user (zero grant on the central database, by design) failed to connect/query at all with a `SQLSTATE[HY000] [1044]` access-denied error referencing the CENTRAL database, because the connection's own `database` config was set to the central database's name purely for DSN purposes. `Stancl\Tenancy\TenantDatabaseManagers\MySQLDatabaseManager`'s methods (`databaseExists()`/`createDatabase()`/`deleteDatabase()`) are all fully identifier-qualified and never actually depend on this value - it only affects what MySQL checks access against at PDO-connect time. Setting it to an empty string produces the same DSN behavior as omitting it entirely (verified via a direct PDO test using Laravel's exact DSN-building logic), so the connection now selects no default database, matching what this connection is actually used for. Never caught before this, since every prior environment used `DB_PROVISION_USERNAME=root` (universal access), for which this specific access-control path is unreachable.

**C70. Tenancy is pre-initialized on `Illuminate\Routing\Events\RouteMatched`, gated on tenant status via a new shared `TenantHostResolver` service, rather than deferred entirely to the normal middleware pipeline (TASK-MVP-004B, RISK_REGISTER.md R57).**
Why: found live on the pilot tenant's first-ever real Admin dashboard visit - `Route::gatherMiddleware()`, part of Laravel's own routing internals, eagerly, fully container-resolves the matched controller (to inspect its middleware) BEFORE any middleware, including `InitializeTenancyByDomain`, ever runs. `Webkul\Admin\Http\Controllers\DashboardController`'s constructor chain reaches `Webkul\Core\Core::getAllChannels()`, a real query, while the connection is still central - raw-500ing on a table that only exists per-tenant. This is unconditional Laravel behavior (`method_exists($controllerClass, 'getMiddleware')` is true for every controller extending Laravel's own base `Controller` class), not something fixable by reordering middleware. The chosen fix moves tenancy initialization earlier than that eager probe, for a Ready tenant only - explicitly reviewed against, and proven not to violate, this project's own pre-existing invariant (TASK-ARCH-013/014, C27-C29-family) that a non-ready tenant's database must never be touched before central rejection. This proof (not just the fix) was demanded and delivered as its own dedicated FIX REVIEW before any deployment was permitted - the strictest evidentiary bar applied to any single fix in this project's history: real-subprocess reproduction (Pest's in-process testing does not reproduce this bug at all), exact Laravel source-level ordering verification, all 6 non-ready statuses proven (via query-connection-log instrumentation, not inference) to never touch the tenant database connection or set `tenancy()->initialized`, 2 distinct Ready tenants proven correctly isolated, central routes proven immune even under Host-header manipulation, unknown domains proven unaffected, and `Tenancy::initialize()`'s own idempotency guard read directly from vendor source to prove the later, normal middleware-driven initialization is a safe no-op rather than a double bootstrap. `TenantHostResolver` (new) exists specifically so `TenantAccessGate` and this early listener can never independently drift into two different Ready/Suspended/etc. eligibility matrices - it owns exactly one decision (resolve + is-Ready), while `TenantAccessGate` keeps 100% of its own response-selection logic (423 vs 503 vs pass-through) unchanged.

**C71. A separate, pre-existing gap - a non-ready tenant hitting `/admin/dashboard`/`/admin/reports` specifically still returns a raw 500 instead of 423/503 - is recorded (RISK_REGISTER.md R58) and deliberately left open rather than folded into R57's fix (TASK-MVP-004B).**
Why: found while proving R57's fix does not weaken the non-ready-tenant invariant. `git stash`-reverting R57's fix entirely and re-testing confirmed this exact symptom already existed, byte-for-byte, on the completely unmodified codebase - it is not a regression introduced by R57, and R57's fix (which only controls WHEN tenancy initializes for a READY tenant) has no mechanism by which it could have introduced it or could close it. The underlying cause is the same Laravel routing mechanic R57 documents (`Route::gatherMiddleware()`'s eager, crashing controller construction happens before ANY middleware, including `TenantAccessGate`), just triggered by a non-ready tenant instead of a ready one. The critical, security-relevant property - no tenant database access for a non-ready tenant - was independently proven still intact (query-log instrumentation showed zero tenant-connection queries across all 6 statuses on this exact route). A real fix needs its own `RouteMatched`-level short-circuit reusing `TenantAccessGate`'s response-building for non-ready tenants specifically - large enough, and independently reviewable enough, to deserve its own dedicated follow-up task rather than silently expanding R57's already-large, already-strictly-reviewed change. Recorded rather than silently patched, per this project's standing practice of disclosing every finding discovered along the way (R23/R28's precedent), even ones judged correctly out of scope for the task that found them.

**C72. `MissingProviderCredentialsException` is now caught locally inside `CheckoutController::store()`, not via a global `bootstrap/app.php` exception-render registration (TASK-MVP-004B, RISK_REGISTER.md R59) - superseding TASK-MVP-004A's original design.**
Why: R52's original fix (TASK-MVP-004A) used `$exceptions->render(MissingProviderCredentialsException::class, ...)` because `CheckoutService` was a typed METHOD parameter of `store()`, so Laravel resolved it (and could throw) before the method body ran - a global render callback seemed like the only interception point available at the time. Found live on the real pilot server that this was the EXACT SAME registration-order-fragile pattern R53 (also TASK-MVP-004B) had already proven broken for a different exception: `Webkul\Core\Exceptions\Handler::register()`'s own catch-all is registered synchronously during Handler construction, strictly before `bootstrap/app.php`'s `afterResolving()`-driven `render()` calls, and always wins under real `APP_DEBUG=false` - producing a raw 500 instead of R52's intended graceful redirect. Unlike R53's case (a vendor-thrown exception with a purpose-built `$onFail` extension point to intercept it before Laravel's exception pipeline at all), `MissingProviderCredentialsException` originates in this codebase's own `StripePaymentProvider` constructor - so the fix instead removed the typed-parameter auto-resolution entirely, resolving `CheckoutService` as an ordinary statement inside `store()`'s own body, wrapped in a narrowly-scoped try/catch. This sidesteps global exception-handler registration order completely, rather than trying to win a race against it a second time. A full-codebase audit confirmed `CheckoutController::store()` is the only real caller of `CheckoutService`/`PaymentProvider`, so the old `bootstrap/app.php` registration was removed outright rather than left as a second, dead, contradictory mechanism. General lesson (sharpening R53's): prefer a local catch at the one real HTTP boundary over a global `$exceptions->render()` registration whenever such a boundary exists - reserve the global-render approach for exceptions with no local catch point (vendor-thrown, pre-controller, or with a dedicated extension point like stancl's `$onFail`).

**C73. R58 is closed by having the SAME `RouteMatched` listener that pre-initializes tenancy (R57/C70) also reject non-ready tenants immediately, by THROWING a custom exception with its own `render()` method - not by returning a response from the listener, and not by registering a new global `bootstrap/app.php` exception-render callback (TASK-MVP-003B).**
Why: R58 (C71) left a non-ready tenant hitting `/admin/dashboard`/`/admin/reports` still raw-500ing, because `TenantAccessGate` never got the chance to run before Laravel's own eager controller-middleware-gathering step crashed. Two mechanisms were ruled out first, both by reading vendor source directly rather than assuming: (1) returning a response from the `RouteMatched` listener does nothing - confirmed via `Illuminate\Routing\Router::runRoute()`'s own source, which dispatches that event with `$halt` defaulted to false, so `Illuminate\Events\Dispatcher::invokeListeners()` silently discards every listener's return value; (2) a new `bootstrap/app.php` `$exceptions->render()` registration would risk the EXACT SAME registration-order race R59 (C72) already proved live for a different exception. The chosen mechanism - throwing `Platform\Tenancy\Exceptions\TenantNotReadyHttpException`, which implements its own `render(Request $request)` method - sidesteps both problems: `Illuminate\Events\Dispatcher::invokeListeners()`'s listener-calling loop has no try/catch, so the exception propagates normally to Laravel's own exception-handling pipeline, and `Illuminate\Foundation\Exceptions\Handler::render()`'s own source confirms `method_exists($e, 'render')` is checked and honored UNCONDITIONALLY, structurally before `renderViaCallbacks()` (where the registration-order race actually lives) - immune to it by construction, not by luck. The actual 423/503 response body is built by a new shared `Platform\Tenancy\Services\TenantUnavailableResponder`, extracted out of `Platform\Tenancy\Http\Middleware\TenantAccessGate` (which now delegates to it too, rather than owning its own copy of the same match statement) - so the early-rejection exception and the middleware can never independently drift into two different response bodies for the same tenant status. `TenantAccessGate` itself is otherwise unchanged in every observable way (same statuses, same codes, same bodies, same fail-closed default) and remains a full, independent defense-in-depth check for any request that somehow reaches it without having already been rejected earlier.
